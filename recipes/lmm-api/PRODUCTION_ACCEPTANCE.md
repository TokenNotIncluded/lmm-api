# 最终验收合同

[PRODUCT_REQUIREMENTS.md](PRODUCT_REQUIREMENTS.md) 及各组件配方中的每一项必需行为，都应有对应于同一最终候选的证据。源码存在、配方结构、测试数量或健康接口，都不能代替业务完成，也不能把各领域取平均折算成完成百分比。本文件只定义通过条件；动态状态仅在[源码进度列表](https://github.com/TokenNotIncluded/lmm-api-source/blob/main/docs/progress.md)中维护，也不构成任何生产操作的授权。

## 能力与证据

| 领域 | 必须证明的结果 | 可接受的证据 |
| --- | --- | --- |
| 权限 | 平台、团队、开发者的动作与资源归属；deny 优先；逐项特权批准；撤权、CAS 与并发 | 真实应用加隔离 PG；成功与拒绝之后，权限、审计和全部状态均可回读 |
| 身份 | 旧身份映射；密码、Session、Key、OAuth、MFA、Passkey；安全激活；旧凭据处置 | 固定的来源、目标、映射与合同；实际登录与撤销；跨租户和错误凭据被拒绝 |
| 资金 | 钱包、欠款、返佣、订阅、Key 限额、预留及持续托管权利逐笔对账，只写入唯一账本 | 授权的只读来源和全新的隔离目标；单位依据、未结算权利、target 导出及应用实际余额 |
| 历史 | 日志、用量、财务导出的范围、时区、单位与权限完整 | 与真实来源目标对照；分页、筛选、权限和完整回读，不能只比较重算出的 plan |
| 支付 | 各 provider 的验签、订单与回调、退款，以及 UNKNOWN 恢复 | 先用合成真进程验证；外部 sandbox 与真实 provider 分别获得授权后验证；原操作最终落入唯一的账本终态 |
| 商业扩展 | 商店、客服、运营、订单与商业资金形成完整闭环 | Core+Go 真进程和独立库；重复、撤权、退款、重启，以及数据库最终状态 |
| 模型 | 所需的 provider、模型、协议方向，以及完整的流式计费 | 固定矩阵下的 JSON/SSE/取消/重试/usage/价格，加真实 provider 证据 |
| 助手与工具 | MCP、工具、赞助付款方、远程控制与 HumanGrant 安全委托 | 真实链路与状态回读；恶意输出、跨租户、撤权、限额和中断恢复的反例 |
| 安装与恢复 | owner/runtime 分离；普通启动无 DDL；匹配的升级；Core 独立运行；实际恢复 | 新装与既有候选升级；低权限被拒绝；备份实际还原；进程、连接及业务回读 |
| Web/CLI | 所有真实路由、动态页与操作；各角色；七种语言；桌面、窄屏与错误状态；客户端的完整目标 | 按实际路由生成清单；浏览器截图、异常与数据库回读；CLI 真实任务及各目标平台 |
| 联合交付 | 同一份最终源码、制品、配置、来源与目标满足全部合同 | 冻结的清单；开发与独立复验；最终组合与故障测试；输入无漂移 |

## 迁移与切换演练

1. 固定需求、候选源码、工具链、依赖、Core/Go/CLI/Web 制品与 schema，并核实实际的进程身份。相同的 schema-manifest 只能证明安装结构一致，不能证明二进制来自当前的完整源码。
2. 固定授权的只读来源、归档、表/字段/行/序列/单位/UTC、完整的身份映射和目标实例。原始秘密保存在私有归档中；派生计划的任何字段或 metadata 都不得夹带已知的 bearer，异常信息和报告也不得泄露原始材料。
3. 逐领域对账。源与目标同样非法的 Key 限制字段不能标为 matched；即使 stored facts 相符，仍须证明完整的导出范围、目标来源、实际权限和单位。未知的事实不得按零、禁用或默认单位补齐。
4. 迁移按依赖顺序执行：身份/console，资金/Key/订阅/历史来源，再到各独立业务库；全程使用同一归档与映射，审批 activation-last。每批的原 SQL 与原 ID 保持固定；须支持精确重放、冲突拒绝，不触及无关的表和序列，且全部金额守恒。后续批次或应用开始写入之后，早期的严格回放即关闭，不能回头重做。
5. 最终的 writer fence、旧 worker，以及回调、请求和退款的 drain，都必须真实读回；要求 active writers=0、unknown liabilities=0。已知的未结算与持续权益，在同一原操作下保留恢复能力，不得重复扣款。接管死亡的 holder 须有死亡证明，并且只做一次 CAS。
6. 实际还原匹配的加密备份，核对身份、资金、Key、订阅、历史、序列、角色与 ACL，并重启业务验证。说明切换后新账本的恢复方法；回退二进制不等于数据可逆。独立的升级历史及外围栅栏，不能随目标的旧备份一起回退。
7. 在新的隔离候选上完整演练边缘路由与回调的切换、业务、重启、故障及恢复，并保存实际运行配置和制品身份。目标生产主机、服务、包、凭据引用、路径与约束，须在获得授权后读回；本地通过不能推定远端也满足条件。
8. 预检须拒绝 `extensions.host_credential="absent"` 以及每一项缺失的必要权限。`core-cutover-preflight` 给出的 READY/safe_to_cutover，只说明受信任输入之间合同一致；仍须核对所引用的证据、目标、时效和最终组合，手写的布尔值或形状正确的 hash 都不是切流证明。
9. 生产执行须有用户明确授权，并使用同一份已审核的候选；切换后观察关键业务、进程与版本，以及恢复条件。未切换时，只报告已证明的前提和未执行的范围，不得称为已上线。

## 资源与新旧性能

| 范围 | 硬条件 |
| --- | --- |
| 单 Core | 1 CPU、256 MiB cgroup 硬限额 |
| Core+Go 产品组 | 共享 1 CPU、512 MiB；数据库、生成器与合成上游的预算单列 |
| 整机目标 | 在 1C1G 下另行验证代表性业务；产品组通过不抵扣整机 |
| 完整 HTTP/SSE 负载 | 60 秒预热、300 秒稳态、60 秒过载、60 秒恢复、60 秒排空；正常为 5 RPS，80% JSON、20% SSE |
| 正常阶段门槛 | 完整成功率 ≥ 99%，P95 ≤ 1 秒，P99 ≤ 2 秒，并满足完整响应与账本断言 |

同时观察慢消费者与取消、过载、恢复与排空、内存增长、FD 与连接、数据库连接以及 cgroup 事件。不得靠全部返回 503、缩减功能、提前关闭保留的客户端或抬高阈值来通过。新环境须记录同等或更明确的 workload 与门槛。

与旧架构比较时，须使用可追溯的优化构建，并保持 CPU、内存、数据规模、功能与计费语义、预热和请求负载一致。分别报告成功、拒绝与超时，吞吐，P50/P95/P99，常驻与峰值 RSS/PSS，长时间稳定性和故障恢复，并保存原始采样。未实测不得写提升百分比，debug 或合成结果不得冒充生产性能。

## 记录与关闭条件

每项证据都记录：固定输入、expected/observed、命令与 cwd、真实工具版本、退出码、日志、数据库/进程/页面的身份，以及独立复验人。PASS/FAIL/BLOCKED/NOT RUN 须明确区分；合成单元、真实 PG、实际 OS 进程、浏览器、外部服务和生产须分别记载。证据复核不能称为独立重跑，对象重建不能称为 OS 重启。

必要项未执行、证据缺失、输入漂移，或严重的资金/权限问题未解决，整体都保持未完成。质量债务按各自的退出条件，映射真实证据、补验并审查；不能靠延后期限、降低等级或手填回执来消除阻断。须保留失败和跳过的记录，不得删除断言，也不得用 success-only mock 或无依据的 skip 凑出通过。

历史任务原文与既往回执的来源，见 [PRODUCT_REQUIREMENTS.md](PRODUCT_REQUIREMENTS.md#历史保全)；当前进度只在源码列表中更新。
