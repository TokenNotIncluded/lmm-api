渠道复制须同时满足原生配置和既有兼容入口：

- 原生 `POST /core/v1/admin/routing/channels/{id}/copy` 接收 `expected_version: {routing, pricing}` 和原样 `suffix`，返回新渠道 `id` 与发布 `version`。路由版本恰好递增一次，价格版本不变；过期版本拒绝且无新增渠道或密钥。
- 副本保留 endpoint、协议、启用状态、模型上下文和全部路由目标参数，名称为原名称加后缀；生成名称的渠道同样有准确预览。副本有独立的加密密钥记录，原渠道更换密钥或停用后仍可使用；不得向客户端返回明文密钥。
- 兼容 `POST /api/channel/copy/{id}?suffix=...&reset_balance=...`；省略后缀为 `_复制`，显式空后缀保留原名称，Web 默认明确提交 `_copy`。旧余额、用量计数的重置和保留语义仍须完整支持，不得复制或改写历史账单。
- 敏感写权限、会话撤销、重复提交、失败回滚和响应丢失均按原合同验证；未知结果不得自动重派。Web 失败保留同一会话的输入，换会话清空草稿，并验证新 ID 与发布收据后再显示成功。

账号申诉（#971）须保留被封禁用户的真实路径：

- 密码、已绑定 OAuth、Telegram 和通行密钥验证身份后，被停用的普通用户只得到十分钟、HttpOnly、限定路径的申诉证明；不签发普通 Session、Key、refresh 或跳过正常登录的 MFA。OAuth-only 用户不被要求设置本地密码，关闭账号和特权恢复边界不变。
- 公开 GET/POST `/api/user/account-action-requests/appeal` 分别读取证明上下文和提交原因；POST 要求合法 Origin、JSON 和真实身份证明，普通 Bearer 或用户名不代替证明。仅显示明确公开的封禁说明；内部操作原因和审核备注不得泄露，也不得复用上一轮封禁原因。
- 同一停用版本并发提交只有一条待审记录，保留原始原因；重复证明不得改写证据。界面按真实收据显示待审、通过、拒绝或已失效，不把失败当成功，不自动刷新凭据后重派提交。
- 管理员列表提供状态和分页。审核核对请求 revision 与身份 auth_version，拒绝过期审核；通过、旧凭据撤销、请求决策与审计原子提交，之后须重新登录。拒绝、重复审核、角色与跨账号权限、闭户、过期证明、公开收据隐私及账本不变均须实测。
- 正式42组件新建安装、明确41→42离线升级及固定32前驱升级须验证，保留原数据、序列、所有权与 ACL。本地 PG/HTTP 通过不代替浏览器、具体账号复核或生产部署；未实际复核的 issue 部分保持打开。
