## 渠道复制

渠道复制须同时满足原生配置和既有的兼容入口：

- 原生接口 `POST /core/v1/admin/routing/channels/{id}/copy` 接收 `expected_version: {routing, pricing}` 和原样的 `suffix`，返回新渠道的 `id` 与发布 `version`。路由版本恰好递增一次，价格版本不变；过期版本被拒绝，且不新增渠道或密钥。
- 副本保留 endpoint、协议、启用状态、模型上下文和全部路由目标参数，名称为原名称加后缀；自动生成名称的渠道同样要有准确的预览。副本拥有独立的加密密钥记录，原渠道更换密钥或停用后，副本仍可使用；不得向客户端返回明文密钥。
- 兼容接口 `POST /api/channel/copy/{id}?suffix=...&reset_balance=...`：省略后缀时为 `_复制`，显式的空后缀则保留原名称，Web 默认明确提交 `_copy`。旧的余额与用量计数的重置和保留语义须完整支持，且不得复制或改写历史账单。
- 敏感写权限、会话撤销、重复提交、失败回滚和响应丢失，均按原合同验证；结果未知时不得自动重派。Web 在失败时保留同一会话的输入，换会话则清空草稿，并且在验证新 ID 与发布收据之后才显示成功。

## 账号申诉（#971）

须保留被封禁用户的真实申诉路径：

- 用户通过密码、已绑定的 OAuth、Telegram 或通行密钥验证身份后，被停用的普通用户只获得一个有效期十分钟、HttpOnly、限定路径的申诉证明；不签发普通 Session、Key 或 refresh，也不跳过正常登录的 MFA。OAuth-only 用户不被要求设置本地密码；关闭账号与特权恢复的边界不变。
- 公开的 GET/POST `/api/user/account-action-requests/appeal` 分别用于读取证明上下文和提交原因；POST 要求合法的 Origin、JSON 和真实的身份证明，普通 Bearer 或用户名不能代替证明。只显示明确公开的封禁说明；内部操作原因和审核备注不得泄露，也不得复用上一轮封禁的原因。
- 对同一停用版本的并发提交，只产生一条待审记录并保留原始原因；重复的证明不得改写证据。界面按真实收据显示待审、通过、拒绝或已失效，不把失败当作成功，也不在自动刷新凭据后重派提交。
- 管理员列表提供状态与分页。审核时核对请求的 revision 与身份的 auth_version，拒绝过期的审核；通过、旧凭据撤销、请求决策与审计须原子提交，之后用户须重新登录。须实测：拒绝、重复审核、角色与跨账号权限、闭户、过期证明、公开收据的隐私，以及账本不变。
- 须验证冻结的 42 组件新建合同、明确的 41→42 离线升级，以及固定的 32 前驱升级，并保留原数据、序列、所有权与 ACL。本地 PG/HTTP 通过，不能代替浏览器、具体账号的复核或生产部署；未实际复核的 issue 部分保持打开。

## 渠道快照补充验收

- 在隔离库中，对同一来源分别以 reset_balance=true/false 以及旧接口的 0/1 表示法复制；明确检查缓存余额、原观测时间、准确的 credits、退款基线和历史完整性标志。
- 复制之后，来源再发生消费、退款或余额刷新，子快照不得变化；子渠道自己的消费只在原账本中计一次。
- 检查：删除高编号后不再复用；显式重建已退役的编号会被拒绝；旧 bootstrap 不能重新启用已退役的编号；未发布 bootstrap 的真实调用，先在原预留事务中记录编号。
- 并发 CAS 只允许一个发布；审计失败时，回滚全部新元数据和秘密，原有的资金与订阅记录逐行不变。
- 外部余额的网络等待不占用事务；等待期间配置或密钥发生变化时，旧结果不得覆盖缓存。
- Native 窗口不包含继承的基线，未知的历史不得伪造完整的 used_quota。
- 真实浏览器、多语言、历史导入以及全部传统渠道功能，继续按原合同验收。
