# Core 验收要求

1. 无配置 --help/--version 成功；非法 TOML、秘密权限不符和缺失配置失败且日志脱敏。
2. 新空隔离库 owner 初始化原子完成；中途失败无部分安装；普通启动/check-db 不写库。错误 schema/runtime 权限失败无 DDL。升级仅匹配前置契约。
3. 个人/团队/管理员/开发者矩阵，凭据过期/撤销、跨租户、IP 不允许、无 scope、非法原生读 Bearer 均拒绝；拒绝后资金不变。
4. 带报价的非流式和 SSE 请求：真实隔离库回读预留、预算、分项、账本；重复 key 仅一次，冲突 key 拒绝；并发消费不超预算。
5. SIGKILL/COMMIT ACK 丢失/流断开后按原 operation 恢复，UNKNOWN 不重复扣费、不换付款方、不无证释放；退款和结算不超原金额。
6. 去掉 Go 及扩展数据库，身份与已授权合成模型正常；关闭模型时 model-ready 503；不能以 ready 200 宣称模型成功。
7. 公开和会话/Key pricing 分权；未知余额单位、数据库不可用、无资金 capability 不伪造 0 或免费调用。
8. 历史数据仅在只读源副本与新目标验证，冻结 source/mapping/instance/SQL；重复回放和冲突拒绝回读全状态；旧 Key、会话、资金不能随身份默认迁移。
9. 源码版本、命令、工具、真实进程与库身份、退出码和日志绑定。合成供应商与真实外部供应商分别列明。
10. 用真实回环 HTTP 分别发送多帧同块、逐帧、逐字节和 CRLF 的 Gemini SSE；客户端收到完整文本、finish 和最后 usage。正常终态、缺终态、半帧、损坏 HTTP、非法 UTF-8、非 SSE 和主动取消有明确不同结果；截断不发成功终止、不再次发送上游请求，公开码与日志分别保持 `upstream_truncated`、`upstream_connection_error`、`invalid_upstream_response` 和 `request_cancelled`。TCP/内存账务观察与真实 PostgreSQL 预留恢复验收分开记录。

11. 用正式新装 CLI、正式授权脚本、受限运行账户及实际 Core HTTP 进程验证公开设置：真实 Session 登录、身份拒绝矩阵、双公告别名、no-op、validate 不保存、错误批次原子拒绝、并发 CAS、审计失败回滚和重启持久性。代理必须观察数据库真实 COMMIT 成功后截断回执，HTTP 返回 `SYSTEM_OPTIONS_COMMIT_UNKNOWN`，另一个连接证明内容与审计已提交，不自动重放。直接 SQL 的受信任 Core 能力与 HTTP actor 审计分别记录；新装、浏览器、已有站点升级及最终组合各有独立结果，不互相抵扣。

12. 运行实际 Core CLI 和真实 History API，在两个隔离 PostgreSQL 物理实例验证安装、只读查询、角色隔离、绑定拒绝、并发只消费一次、真实目标 PGDATA 恢复不清空原操作、历史库实际进程停启后原状态保持。真实转发 COMMIT 再丢弃上游完成回执，API 返回结果不确定，新连接看到已消费，重做仍拒绝。开发和独立 owner 分别记录；合成扣账与围栏 hash 不能替代产品资金迁移或部署停写证据。

13. 通过真实 `upgrade-offline` CLI 验证固定旧 Core 前驱到新安装合同，核对新装与升级后的同一固定 catalog；v5/26 的 21 个序列和 v6/27 的 22 个序列分别保持。运行真实旧 Core 服务，验证制品身份、持久 mask/停机、目标数据库禁连、库外 HBA 的加载与正反连接探测。真实目标 COMMIT 成功后丢回执，应保持外部 STARTED，并由原绑定回执恢复确认，不能重做；历史库 COMMIT 丢回执后必须新连接观察。实际恢复旧目标 PGDATA 后，独立历史和外部 HBA 仍保持，报告提交历史与当前库分歧，禁止开放或换 ID 重试。进程死亡窗口由独立所有者实测。升级后在明确的隔离夹具开放步骤中启动实际新 Core，以受限运行账户完成原密码登录及公开内容保存/读回；私有升级回执保持 owner-only，误授其表级或列级读取权限仍拒绝启动，缺少六张公开合同中任一所需读取权限也拒绝。夹具手工开放不能替代产品 finalization。失败、未运行、目标 PG 范围、全站停写和最终生产门槛分别报告。

14. 以实际 Core、隔离 PG 和带计数/延迟的真实回环 JSON/SSE 供应商验证性能采样、重启持久性、原 request 绑定及只存一次；区分 provider terminal 与 finalization/客户端错误。首个有效 Delta、空/Usage/心跳帧、非流式 TTFT、UNKNOWN 与缺样本必须如合同，读出值与事件及实际时间范围相符。汇总/分组/曲线按分母加权，UTC小时/五分钟/分钟边界及最近三桶正确；个人 Session 当前组和模型可见性限制与拒绝矩阵有效。删除采样或未运行入口保持 partial，不能补零或改写资金。Web 实际渲染未知/部分状态及有效数值，完整历史和S11单列。

上述是重建必须满足的验收条件，不是运行结果。实际源码、命令、通过/失败和未运行范围以主配方项目的 STATUS.md 及关联 PR 为准；单项修复不能代替完整数据库、慢客户端、恢复或独立 Core 资源验收。

15. 全站财务需以真实Core、隔离PG和已冻结合成旧来源独立核对：保留停用身份、钱包/预留/欠款/返佣/团队隔离；完整历史used归一化及其原始rebase/撤销材料；现金多币种、LDC、未确认/非法订单、订阅镜像/赠送排除、Native已核验订单/退款去重，整数总量超JS与SQL bigint仍精确。验证来源缺失/篡改/重放/冲突、snapshot并发一致、全部权限与只读状态不变。正式旧27→新组件升级与回执恢复另验；未提供真实历史来源和生产条件时不宣告完整生产销项。

全站财务另须覆盖导出持续窗口：observed_at 后、来源导入前已存在的 Native 意图不能因此自动算新款；封存后该旧意图才入账保持 UNKNOWN。独立验证空序列、已有编号、源完成时默认上界、后续新编号、NOOP 不重采、序列回退/循环拒绝及受保护序列不变；合成时间 +1/+2 用例不能替代此来源证明。

对字符串请求编号另验目标侧完整集合封存：历史用户在封存前已有的请求后来结算仍保持 UNKNOWN；封存后同一秒的新请求可计入；集合见证缺失须拒绝。经真实 Core 创建、位于完整旧归档之外的 Native 用户即使早于归档存在，也应能保留独立 Native 用量。上述场景通过真实归档与正式 prepare/apply 路径建立来源，不能以任意 SQL 伪造的 complete 来源替代可达状态证明。

Native 先存再首次导入旧站的共存路线另核对完整身份、开账及财务执行与 fresh gate。局部 reader/SQL 用例不能作为该迁移次序的已交付证据。

另用正式 CLI 首次安装、创建管理员、实际密码登录后读取全站财务；只有该原生用户且没有开账、请求和付款时返回成功及准确零值。开发 bootstrap 不能抵扣此路径。保留真实首管登录成功但财务 503 的旧反例，并验证修复未放宽已有导入缺少财务来源时的拒绝。

渠道整合须用实际 Core、隔离数据库和真实请求独立验证：有符号优先级大小、重试降级、可用性过滤后全零和混合零权重、首选及排除渠道；验证 Session、策略撤销与并发变更，控制面状态、路由版本和回执同事务失败回滚及提交不明恢复。分别验证新安装和已批准历史前驱逐段升级，核对原财务数据、视图、授权及既有回执。局部 CRUD、模拟路由或候选补丁测试不替代完整渠道和历史迁移验收。

16. 五类支付 provider 分别验证原始签名、环境/商户/订单/交易、金额/币种/商品、过期与重复证明的接受和拒绝；真实隔离 PG 回读 proof 与账本、跨 intent/provider namespace 的交易去重、重启后原证明消费和一次入账。EPay 密钥只在 Core，实际 RPC 证明个人付款账户来自会话，checkout 仅签既有 intent；Linux DO 的 LDC 与明确 POST 路径、普通 EPay 的 GET 方式分别验证。FastPay 在配置、provider、公开渠道及报价阶段均不能启用。

17. Waffo Global 除验签外，用 Core 私有凭据连接真实回环 inquiry 服务验证商户、merchantOrderId/paymentRequestId、acquiringOrderId、状态、金额和币种；不匹配、无权限、超时、坏 JSON、过大响应或缺配置保持不入账。测试和正式环境选择固定端点，Go 伪造查询结果无效；记录合成服务与真实支付商分别覆盖的范围，不能把本地通过写成真实商户验收。

18. 使用精确 28 组件前驱和实际 Core CLI 执行 `core-payment-gateways-v1`，比对 29 组件新装目标、旧数据/序列/权限不变及私有升级回执。前驱结构被改、角色越权、重复 provider 交易、目标结构被改、请求冲突和新 ID 重做均拒绝；真实 COMMIT 后丢回执，再按原请求恢复 `already_committed`。runtime/Go/PUBLIC 不得读取升级回执，普通启动与 check-db 无 DDL；该升级不替代历史资金导入、整站围栏或生产开放验收。

原生充值财务另核对五 provider 的成功 Core 入账来源：USD/CNY/EUR 分别进入现金币种列表，LDC 只进入虚拟单位列表，支付商已收款但 Core 未入账不能算到账。保持旧 Stripe 退款的已核验来源与累计限制；其余 provider 的退款仍需自己的执行和回冲证据，新增充值通过不能抵扣退款验收。
