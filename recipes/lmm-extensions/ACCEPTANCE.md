# 扩展验收要求

- Core+Go 真进程、独立隔离数据库与不同 runtime 角色验证购买、订单读取、结算和退款；查询前后资金表/序列无写入。
- 团队成员、非创建者、跨租户、撤权/注销、禁止写入、无 Core RPC scope 与凭据伪造均拒绝。
- 回调验签错误、金额/币种冲突、重复/乱序、超时和重启后消费只有一个原 operation 账本结果。
- 退款/扣款 ACK 丢失按原键恢复；失败不能无证释放或创造新付款方。
- Go 停机、排空、Core 暂不可用时准确拒绝并保留可恢复记录；Core 模型不依赖 Go 同步可用。
- 助手历史按所有者脱敏；未启用模型、平台赞助 scope 缺失、模型诱导调用私有工具必须拒绝。
- MCP 工具、公开协议、商店和客服至少覆盖正常、无权限、空、错误、超限、重复和状态恢复。
- 合成协议、真实隔离库、支付商 sandbox、真实外部支付和浏览器各自记录，分别绑定源码、配置、凭据环境、命令与结果。

## 支付覆盖矩阵

按以下矩阵逐行保留开发者自测、真实 Core+Go+PG 联调、进程重启、浏览器及支付商验证状态；入口存在、合成回调通过和 200 就绪响应不能替代其他列。

| 对象 | 需要验证的产品行为 |
| --- | --- |
| EPay | 支付宝/微信 CNY、显式自定义 type、钱包充值、套餐一次性购买；签名、方式/金额/币种/商户/订单绑定和重复回调 |
| Linux DO | EPay 协议、LDC 明确标识与独立定价；普通 CNY 不串用；商店平台精确网关地址、全额退款及不支持部分退款的可见结果 |
| Stripe | 钱包 checkout、异步支付、订阅首次购买/续费/失败/取消状态；钱包退款与订阅退款分别登记证据 |
| Creem | 服务端固定商品及金额、钱包 checkout、订阅远端商品/周期核对、首次购买/续费/状态事件；退款缺口持续保留 |
| Waffo Global | 独立配置、测试/正式环境、服务端子方式、钱包下单/支付/退款回调与企业账单资料；不将其与 Pancake 混为一个 adapter |
| Waffo Pancake | 钱包、套餐 one-time/recurring 映射、首次购买/周期收款、退款、地区/语言/币种、目录与商品绑定、客户 portal、过期订单上游查询 |
| 商店 | 平台余额、商户 EPay、商户 Pancake、平台 Pancake、平台 Linux DO 分别完成购买/交付/退款；支付权、商品库存和 Core 账本一致 |
| FastPay 淘汰 | 运行配置/渠道注册/公开渠道目录/报价/checkout 均不能启用；历史记录只读可识别，未知 provider 拒绝测试保留 |

1. 用各 provider 的签名向量验证原始字节、时间窗、环境公钥/秘密、商户和交易 namespace；错签名、错币种、错金额、跨用户/跨订单/跨产品、重复 ID 不同内容都拒绝。Core 必须持久接纳证明，Go host token 不能生成已付款事实。
2. 用真实独立数据库与 Core/Go OS 进程验证接纳后 ACK 丢失、队列写入后停止、Core COMMIT 后断链、退款发出后响应丢失。恢复读取原 operation，核对账本、支付商调用次数、退款累计额度与 UNKNOWN 预留；对象重建不计为进程重启。
3. 验证渠道配置、秘密引用、环境和商品轮换：新的下单遵守当前配置，原订单继续按已保存的商户/环境/商品/金额证明查询及结算。停止接纳新单不丢弃旧回调。
4. 退款绑定新支付的 Core intent/accepted proof，或历史导入的不可变来源；防止跨来源重复消费。Pancake 的 ticket/通知必须与原 payment 和实际退款执行核对；Linux DO 全额退款不被扩展为任意 EPay 的部分退款。支持范围之外的请求有明确结果，不伪造成功。
5. Web 与真实后台联合验证报价、明确确认、test 标记、固定 Creem 金额、大整数、原请求持久化、401 后显式恢复、账号切换、有限只读轮询。支付商成功但 Core 未入账保持等待；未知/review 保留原单，不悄悄生成第二次付款。
6. 订阅周期、状态和退款逐 provider 验证；旧版没有的 Waffo Global 订阅、Creem 自动退款、Stripe 订阅退款不能从钱包能力推断为完成。已有 A05/A06 目标继续追踪，不能通过标注旧版缺口从完整产品范围删除。

以上是持续验收要求。实际完成、失败、阻塞和未运行项由主项目 STATUS.md 及对应固定源码回执记录；本轮钱包充值实现不抵扣订阅、商店、真实支付商和 Extore 联合验收。吞吐、内存和延迟预算需另行测量。
