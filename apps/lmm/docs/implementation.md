# 实施与验收计划

状态记录：2026-09-19。产品原文见 [requirements.zh-CN.md](requirements.zh-CN.md)。
本文件的“完成”仅指本阶段，不代表原始产品的最终验收。

## 仓库与已有能力

- 子项目：`apps/lmm`；crates.io package：`lmm-cli`；library / binary：`lmm`；独立 Cargo.lock。
  `lmm` 注册名已属于其他项目，因此发布包名与命令名分开。
- 现有 OAuth：`apps/api-go/service/oauth_server.go`、`service/oauth_contract.md`。
  当前源码客户端登记为 `lmm-pi`、`lmm-dsh` 和本次新增的只读 `lmm`；生产是否部署另行验证。
  现有授权码、PKCE、刷新轮换、撤销、目录、relay 和计费能力应复用。
- 现有 scope 按已知应用组合校验，不能只增加 client ID 就声称符合最小权限。
- 当前 balance 契约 `authorization_limit: null`，不代表支持独立应用费用上限。
- Pi / DSH Provider 属于独立子模块。CLI 不读取其私有 refresh token，
  不将 CLI 或其他客户端的长期凭据复制给 AstrBot / CC Switch。

上游路径依据（仅证明发现位置，不证明集成兼容）：

- [AstrBot 配置说明](https://github.com/AstrBotDevs/AstrBot/blob/master/docs/zh/dev/astrbot-config.md)：默认配置位置及多配置语义。
- [CC Switch 存储说明](https://github.com/farion1231/cc-switch/blob/main/docs/user-manual/ja/5-faq/5.1-config-files.md)：默认目录、SQLite 主存储、可定制位置。

## M1：服务端应用授权与无浏览器登录

已实现的 M1 子集（尚未完成本阶段）：

- `lmm` 客户端仅有目录、余额读取和显式同意的分组 scope，服务端拒绝模型调用、MCP 和账户管理。
- 同意页根据实际 scope 显示调用权限；CLI 名称、返回入口与其他客户端分开。
- `login` 复用浏览器登录及回环 PKCE；严格校验 issuer、state、发现端点和令牌范围。
- HTTPS、有界请求/回调、不跟随重定向、系统凭据库和进程锁。
- `models` 只读目录；串行刷新在网络请求前持久记录不可重试状态。
- `logout` 只撤销 CLI 的令牌族；撤销失败保留本地记录，不假称已撤销。
- Rust 临时 HTTP 服务与真实本机回调测试；Go OAuth HTTP 测试验证 CLI 权限隔离、
  钱包不变、刷新、撤销以及不影响 Pi 授权。测试不接触真实账户或收费上游。

仍缺：跨设备授权、应用独立授权与预算、真实系统凭据库/浏览器互操作和三平台运行验证。
没有将 read-only CLI scope 当作后续应用授权管理接口。

本次本地验证：47 个 Rust 测试、Clippy（warnings as errors）、rustfmt、Linux x86_64
release 构建通过。干净 Git 检出仅叠加本次 OAuth 改动后，`oauthserver`、`router`、
`controller`、`service` 四个包测试及 `go vet` 通过；未依赖共享工作区其他未提交功能。
三平台 CI 已配置，但此处不预先声称远端 CI 或实际凭据库验收通过。

在现有 OAuth 实现上扩展，而非另建账号、API Key 或计费系统：

1. 明确 `lmm` CLI 公共客户端和最小管理 scope；调用权限与应用授权管理权限分开。
2. 设备授权流程需有短期用户码、浏览器确认、绑定目标/设备、限速、有界轮询和取消。
   桌面使用回环 PKCE；服务器可在另一设备授权，不要求粘贴 API Key。
3. 应用授权按账号、设备、软件、实例建立稳定身份和唯一约束；同目标重复接入幂等。
   撤销形成持久状态，修复/同步不能隐式恢复。
4. 服务端逐请求强制模型 allowlist、预算和撤销；并发请求预扣/结算/退款与现有计费统一。
   费用预约与应用上限应分开建模，避免把 `balance` 当成消费保证。
5. CLI 登录与应用授权分别存储和撤销；切换 CLI 账号不迁移应用。
6. 凭据保存在平台安全存储；刷新串行化与失败恢复不得重放已消费 refresh token。

验收：两应用隔离撤销、并发预算不能超限、无图形授权、取消/过期、三次重复 setup、
登出后应用可持续运行。需要真实浏览器、服务端和 relay 证据，不能只靠 mock。

## M2：持久状态、计划与执行事务

- 固定环境/设备/实例身份，分开安装管理者、配置管理者与授权管理者。
- 带 schema version 的本地状态、受保护日志和恢复材料；日志不含明文凭据。
- 计划引用配置版本与目标标识；确认后重新读取，冲突停在对应目标。
- 用原生事务或管理接口完成写入；明确无法可靠协调的文件适配器边界。
- 任务持久化：未开始、进行中、等待用户、等待生效、成功、失败、取消、需要恢复。
- 取消后停止发起新写入；一个目标失败不回滚其他成功目标；记录共享依赖关系。
- 付费授权、重启、账户迁移与安装管理权分别确认；无人值守缺授权直接结束。

验收：并发外部修改、中途退出/断电恢复、多目标部分失败、恢复保留后续用户字段。

## M3：AstrBot 端到端

- 固定并验证具体版本；分别实现本机、Docker、显式远程实例管理授权。
- 读取多配置和实际生效关系，新增 provider source、启用模型、按选择修改目标配置。
- 使用原生 API 或受支持 Provider；如需常驻凭据代理，必须独立服务化并纳入生命周期。
- 管理后台默认保持本地，不绕过初始管理账号；保留平台、插件、人格和历史。
- 实例内独立测试会话通过 LMM 调用；禁用其他服务商回退，不发真实群消息或启动旧任务。
- 报告目标配置和会话覆盖边界；等待重载/重启时不得提前标为生效。

验收必须覆盖原文 AstrBot、多实例、费用、重复执行与恢复场景。

## M4：CC Switch 共存

- 固定版本并核实官方导入/管理接口；不直接改未验证版本的 SQLite schema。
- 按目标应用识别管理关系，不以 `.cc-switch` 存在作为全局接管证据。
- 稳定 LMM provider ID，重复导入更新已有项；始终保留当前选择和故障转移顺序。
- 区分 provider 已添加、当前选择、代理实际路由；未知链路不猜。
- 导入确认、重启等待与跨设备独立授权有独立状态；模板不含长期凭据。

验收：普通切换、本地路由、切离 LMM 后同步/修复、跨设备同步、重复导入。

## M5：安装、发布与生命周期

- 每项安装资产固定来源、版本和摘要/签名；稳定兼容矩阵决定版本，不能盲追 latest。
- Windows/macOS/Linux × x86_64/ARM64 分别构建、运行和记录验证证据。
- 普通用户安装不依赖 Rust；受校验的发布二进制、平台安装器与升级渠道。
- 软件独立安装无需登录；外部管理软件未经明确授权不加入批量更新或卸载。
- 更新后目标实际验证，失败保留原环境；安全取消和共享组件引用管理。
- 安装、启动、更新、解除接入、恢复、卸载与 CLI 登出分开实现和验收。
