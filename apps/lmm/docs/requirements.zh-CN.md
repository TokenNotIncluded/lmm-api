# LMM CLI Setup

## 一、产品定位与目标

LMM CLI 是 LMM 生态的统一安装与接入工具，将软件下载、环境准备、账号授权、模型配置和可用性验证整合为一次完整操作。

用户运行：

```bash
lmm setup
```

选择需要的软件，完成必要授权并确认操作后，即可通过原软件使用 LMM。用户无需自行创建 API Key、复制服务地址、查找模型编号或编辑配置文件。

产品复用现有 LMM OAuth 登录能力，使用 Rust 开发。支持用户已有的软件和配置管理方式，不替代 AI 客户端，不要求用户放弃 CC Switch，也不另建充值、计费或聊天系统。

**核心目标：把选定的软件准备到可以实际使用 LMM，并让接入过程可检查、可维护、可撤销。**

“一键”意味着将可以自动完成的工作合并处理，不意味着跳过账号授权、费用确认、系统权限或必要的软件许可确认。

## 二、支持范围

### 跨平台与运行环境

LMM CLI 支持 Windows、macOS、Linux，覆盖 x86_64 和 ARM64 架构。相同任务应使用相同命令，安装方式和环境差异由 LMM 处理。

提供适合普通用户的 LMM CLI 安装方式，不要求用户先安装 Rust 或准备开发环境。

支持有浏览器的桌面设备，以及无图形界面的服务器。服务器用户应能够在另一台设备上完成登录授权，无需手动配置 LMM API Key。

本机、Windows 中的 Linux 环境、容器和远程实例必须分别识别。一个环境中已经安装软件，不代表另一个环境也已安装；配置一个环境，也不得顺带修改其他环境。

### 软件目录

软件目录覆盖 AI 编程工具、Agent 工具、编辑器扩展、桌面客户端，以及 AstrBot、CC Switch 等目标集成对象。

用户能够搜索软件，并查看用途、项目来源、支持平台、兼容版本、必要组件和接入能力。每个条目必须对应明确的项目，不能以含糊名称指向不同软件。

目录必须分别说明：

* **安装能力**：能否自动下载、安装和启动。
* **接入能力**：能否自动连接 LMM，是否需要额外确认或组件。
* **维护能力**：能否检查、更新、修复和恢复。

“可以下载”不能等同于“完整支持”。同一软件的命令行版、桌面版和编辑器扩展也不能默认视为同一项兼容能力。

每项兼容声明都应对应经过验证的软件版本、系统环境和使用场景。未经验证的组合应明确标记，不得通过模糊的“兼容所有版本”掩盖限制。

## 三、核心流程与默认行为

### 1. 发现环境

`lmm setup` 首先识别当前运行环境、已安装软件、现有配置、LMM 登录状态，以及软件是否由 CC Switch 等工具管理。

检测范围默认限于当前用户有权访问的本机环境。远程实例由用户明确指定，不自动扫描局域网或其他设备。

无法读取配置时，应显示“无法确认”，不能直接判定为“未安装”或“未配置”。

### 2. 选择目标

未指定软件时，展示已发现的软件和适合当前环境的可安装软件，由用户选择。

指定软件时，直接进入该软件的接入流程：

```bash
lmm setup astrbot
lmm setup cc-switch
```

存在多个安装位置、用户配置或运行实例时，应让用户选择目标。后续操作始终围绕该目标进行。

默认只修改当前用户选定的软件和配置范围，不修改其他用户、其他项目或系统级设置。发现项目设置覆盖通用设置时，应说明实际生效范围。

### 3. 展示操作计划

修改前集中展示本次计划，说明将安装或更新的对象、使用的账号、修改范围、是否启用 LMM、是否切换模型，以及是否需要重启或付费测试。

用户应能直接使用合理默认值，只在涉及真实选择或风险时确认，不必逐项回答可以自动判断的技术问题。

计划确认后，如果发现新的重大影响，例如需要额外权限、安装其他组件或重启正在运行的服务，应重新确认变化部分。

### 4. 区分添加与启用

新安装且尚未配置模型服务的软件，在用户确认接入计划后，默认启用 LMM。

已有其他服务商的软件，默认保留当前选择，提供“仅添加 LMM”和“添加并切换到 LMM”两种结果。

已经接入 LMM、但用户后来切换到其他服务商的软件，再次执行 `setup` 时必须尊重用户当前选择。

**重复执行、模型同步、软件更新和故障修复，都不能成为强行切回 LMM 的理由。**

### 5. 执行与完成

执行过程中显示当前操作和进度，允许取消。独立的软件任务应分别完成，单个失败不应阻止其他任务继续。

结束后逐项说明已完成内容、实际启用状态、验证范围和待处理事项。需要打开管理页面、重新启动软件或继续授权时，给出直接入口或下一步命令。

不得用一个总的“成功”掩盖部分软件尚未完成。

### 批量与无人值守行为

`lmm setup --all` 仅为当前环境中已安装且受支持的软件批量规划接入，不安装整个软件目录，也不自动包含远程实例。

无人值守模式应要求事先明确目标和授权范围。缺少授权、发生冲突或出现未批准的费用时，应结束相关操作并返回原因，而不是无限等待或默认同意。

## 四、下载安装、组件与更新

### 安装行为

单独安装软件不应要求先登录 LMM；连接模型服务和执行 LMM 调用时才需要授权。

LMM 自动选择适用版本，完成下载、安装和必要依赖准备。默认安装已确认兼容的稳定版本，不为追求最新版本而引入未经验证的变化。

下载来源必须明确可信。安装前检查必要条件，避免明知不兼容仍继续执行。不得夹带无关软件，或通过关闭系统安全保护完成安装。

已有软件优先复用。原有版本不兼容时，说明可选择的处理方式，不擅自降级、重装或另装一份。

### 管理关系

软件的安装管理者与配置管理者应分别识别。例如，软件可以由系统的软件包管理器安装，同时由 CC Switch 管理模型配置。

对外部安装的软件，默认只完成用户授权的接入操作。纳入 LMM 的批量更新或卸载范围，需要明确确认。

### Provider 与插件

需要专门 Provider，即模型服务接入组件，或插件时，自动安装与目标版本匹配的必要组件。

已有兼容组件应复用。不应仅为接入 LMM 安装与本次任务无关的插件、MCP 工具或其他扩展。

若集成需要辅助组件持续运行，应在安装前说明，并将其纳入启动、检查和卸载管理。正常使用不得依赖 `setup` 的终端一直保持开启。

### 更新行为

更新前展示可更新对象、兼容性变化和影响，由用户确认后执行。允许用户保留正常工作的版本，不强制更新。

服务重启、配置迁移或可能影响数据的更新，应单独说明。更新后重新检查 LMM 接入，不能仅凭软件版本变化报告完成。

下载或更新失败时，保留能够继续使用的原环境，并支持重试。

## 五、登录、应用授权与费用

### 登录与持续使用

复用现有 OAuth 登录状态，不要求用户在每个软件中重复登录 LMM。

登录过期与应用授权失效应明确区分。需要重新授权时，保留已经完成的安装和配置，并在授权完成后继续。

AstrBot 等持续运行的应用，在关闭安装终端后仍应能正常调用 LMM。

### 应用级授权

用户应能识别每份授权对应的软件、设备或实例，查看其使用范围，并单独撤销。

不同应用不得默认获得修改账户、安全设置或其他应用配置的权限。重复配置同一目标时，应复用或更新原授权，不不断创建新的授权记录。

支持为应用设置模型使用范围和消费限制。限制必须在 LMM 账户侧实际生效，包括后台运行和从原软件直接启动的情况，不能仅在 CLI 中显示提示。

用户主动撤销授权后，`setup`、同步和修复不得在未经确认的情况下重新授予权限。

### 账号切换

切换 CLI 登录账号不应自动迁移所有应用。

需要将某个应用改为使用新账号时，应明确展示受影响对象、新的费用承担账号，以及原授权如何处理。

### 费用确认

默认模型和付费测试应展示计费信息，单位清楚，不要求用户自行换算不明倍率。

`setup` 中的付费验证可以合并进操作计划一次确认，但应说明测试范围和消费上限。无法确定或约束费用时，不自动执行付费测试。

额度不足时，保留已完成的安装和配置，标记等待处理。不得自动充值、切换其他账号或换用未经确认的收费模型。

## 六、模型选择与同步

按目标软件的用途和必要能力，展示当前账号有权使用的兼容模型，避免让用户从整个模型目录中自行判断。

默认建议应说明实际模型名称、主要用途、必要能力和价格，允许按软件或实例分别选择。

模型同步负责更新可用信息，不默认改变用户已选择的模型。新增模型不应自动替换现有模型；模型下线、权限变化或不再兼容时，应说明影响并提供替代选择。

模型别名应能查看当前对应的实际模型。同步或别名变化导致实际模型改变时，应让用户可见，不得把“名称没变”当作“配置没变”。

仅维护 LMM 相关模型和服务项，不覆盖其他服务商，也不把全部模型无差别添加到每个软件。

## 七、AstrBot 快速接入

### 接入目标

通过 `lmm setup astrbot`，使指定 AstrBot 实例中的目标配置能够实际使用 LMM。

AstrBot 的模型接入包含添加提供商、启用模型，以及在目标配置中选择对话模型。因此，不能只完成服务商添加就报告接入完成。

### 实例与授权

支持本机部署、Docker 部署，以及用户指定并授权管理的远程实例。

已有实例优先接入，不另建一套。新安装实例应完成必要的运行准备，并明确后续启动和访问入口。

LMM 账号授权与 AstrBot 管理授权分别处理。不能因为用户登录了 LMM，就假定其有权修改任意 AstrBot 实例。

新部署不得为了方便接入而默认将管理后台开放到公网，或绕过必要的管理账号初始化。

### 配置生效范围

自动新增或更新 LMM 服务项，获取并启用用户选择的模型，再按确认范围设置目标配置。

AstrBot 的聊天界面可以分别选择配置、服务商与模型，部分情况下还存在会话独立选择。因此，改变默认配置不能被视为所有会话都会同步改变。

接入时应说明影响的是哪套配置，以及既有会话是否会继续保留原模型。不应默认修改所有机器人和所有会话。

保留消息平台连接、插件、人格设置、其他服务商和历史数据。

### 验证与交付

验证必须以选定实例的运行环境和目标配置为准，确认请求实际通过 LMM 完成。

仅由安装电脑调用 LMM 成功，不算 AstrBot 验证通过。使用其他服务商自动接替后取得回复，也不能算 LMM 接入验证通过。

需要重新加载或重启时，说明影响并取得确认。尚未生效的配置标记为“等待生效”。

完成后展示实例、目标配置、实际模型和验证结果，并提供打开 AstrBot 的入口。

**模型接入完成不等于消息平台机器人已经上线。** 验证不得向真实群聊或联系人自动发送消息，不自动执行用户已有的机器人任务。

## 八、CC Switch 兼容

### 接入原则

CC Switch 已提供服务商导入、配置和切换能力。LMM 的目标是在其中添加可用的 LMM 服务项，而不是接管或替代这些能力。

检测到 CC Switch 时，按目标软件分别判断管理关系。不能因为安装了 CC Switch，就假定所有软件都由它管理。

由 CC Switch 管理的配置，必须通过兼容方式维护，不同时从其他位置覆盖。

### 普通切换与本地路由

兼容普通服务商切换，以及 CC Switch 本地路由启用时的工作方式。

CC Switch 的本地路由会将应用请求转交给当前启用的服务商，因此不能仅凭应用中保存的服务地址判断实际使用对象。

LMM 的状态检查应区分“LMM 已添加”“当前选择 LMM”和“本次调用实际经过 LMM”。无法确认实际路径时，应明确说明。

用户切换到其他服务商后，同步、更新和修复不得切回 LMM，也不得改变原有自动切换顺序或其他服务商设置。

### 配置与授权更新

重复添加同一目标时，应更新已有 LMM 条目，不产生重复服务商。

需要在 CC Switch 中确认导入、启用或重启时，应引导完成，并显示“等待操作”，不能提前报告成功。

授权变化只更新对应 LMM 接入信息，不改变当前选中的服务商，不覆盖 MCP、Skills、提示词或其他无关设置。

CC Switch 支持跨设备同步配置。LMM 应区分“配置已经同步”和“当前设备已经完成授权”，不能将两者视为相同状态。可分享的配置模板不得包含 LMM 账户的长期登录凭据。

## 九、状态、验证与诊断

### 状态应分别展示

软件安装状态、LMM 接入状态和验证状态必须分别显示，至少让用户知道：

* 软件是否安装，目标环境是什么，由谁管理安装和配置。
* LMM 是否已添加、已授权、已启用，当前服务商和模型是什么。
* 最近检查的时间、检查范围，以及哪些内容尚未验证。

用户主动使用其他服务商，不应被标记为故障。没有权限读取、网络暂时不可用或尚未检查，也不能被误报为正常。

状态查询不得触发付费模型调用。历史验证通过应显示检查时间；配置、模型或软件版本变化后，应提示需要重新验证。

### 分清验证层次

验证结果至少区分配置检查、LMM 连通性验证和目标软件实际调用验证。

**只有目标软件在所选使用场景下验证通过，才能标记该场景“已可使用”。**

对于声明支持编程工作流的软件，验证不应止于一次简单文本回复，还应覆盖所承诺的流式输出、工具调用和必要的多轮交互。额外能力未验证时，应单独标记，不得概括为全部兼容。

验证应使用专门的测试内容和临时环境，不读取真实项目、不修改用户代码、不调用具有真实外部影响的工具。

选择“仅添加但不启用”时，不得为了测试擅自切换当前服务商。

### 诊断与修复

`lmm doctor` 默认只检查，不修改配置，也不触发未经确认的付费测试。

问题应指出出错位置、影响和下一步，例如登录失效、余额不足、模型无权限、目标配置未生效、必要组件未运行或网络连接失败。

`lmm doctor --fix` 只修复明确属于 LMM、且已获允许的内容。涉及重装、重启、账号切换、服务商切换或覆盖用户修改时，仍需确认。

不能通过反复重置本地配置来处理 LMM 服务端或上游故障。重试必须有明确终止条件，不得无限重试或反复产生费用。

支持生成经脱敏的诊断摘要，供用户主动分享。摘要应包含必要的环境和错误信息，不包含完整凭据、对话内容或项目代码。

## 十、配置保护、恢复与退出

### 变更记录与保护

修改前保存可恢复的原状态，并记录本次修改的对象、范围和结果。用户能够知道某次操作影响了什么。

执行期间，如果用户或其他管理工具修改了相同内容，应暂停冲突部分并重新确认，不能覆盖刚产生的新设置。

配置失败时，仅撤销该目标本次未完成的修改，不影响其他已经成功的软件。依赖同一组件的任务，应准确标记受到的影响。

### 恢复

`lmm restore` 用于撤销用户选定的 LMM 配置修改，而不是用旧备份覆盖整个环境。

用户在接入后新增或修改的设置应保留。存在冲突时，展示差异并允许选择。无法完整恢复的内容，应在执行前说明。

恢复旧配置不得重新激活已经撤销的授权。配置能够恢复，不代表旧授权仍然有效。

### 退出、解除接入与卸载

这几种操作必须明确区分：

**退出登录**：退出当前 CLI 登录状态，默认不终止持续运行应用的独立授权，并明确告知仍有效的应用。

**解除接入**：撤销指定应用或实例的 LMM 授权，移除其 LMM 接入信息，保留软件及其他服务商。正在使用 LMM 时，应先说明影响，让用户决定是否切换到已有的其他服务商。

**恢复配置**：撤销特定配置变更，不自动删除软件或历史数据。

**卸载软件**：删除用户确认的目标软件，默认保留用户数据，不误删共享组件，也不卸载仅被发现但未获管理授权的软件。

卸载 LMM CLI 本身时，应说明哪些应用仍可独立运行、哪些依赖 LMM 组件，以及尚未撤销的授权。不能留下用户不知道的持续授权或运行依赖。

网络不可用时，应区分“本地信息已移除”和“服务端授权已撤销”，不能将尚未确认的撤销报告为完成。

## 十一、重复执行、安全与隐私

所有安装、配置、同步、更新和修复操作都应支持重复执行。有效的已有状态应复用，不新增重复服务商、插件、授权或软件副本。

中断后应能够继续未完成部分。用户取消后，停止发起新的修改，并说明哪些内容已经完成、哪些需要恢复。

不得在普通输出、诊断报告、分享模板或更新日志中暴露完整凭据。包含敏感信息的配置备份应受到保护，不能作为普通日志自动上传。

默认不采集用户对话、代码或与环境诊断无关的数据。问题报告、使用统计或错误上传均应让用户知情并可控制。

`--all` 只扩大操作对象范围，不代表允许忽略权限、覆盖冲突、删除数据或跳过费用确认。

## 十二、命令约定

| 命令                    | 预期行为                                    |
| --------------------- | --------------------------------------- |
| `lmm setup [软件]`      | 完整接入入口。发现环境，按需安装，完成授权、配置和验证。未指定软件时提供选择。 |
| `lmm setup --all`     | 为当前环境中已安装且受支持的软件批量规划接入，确认后执行。           |
| `lmm install [软件]`    | 安装软件及必要运行组件，不要求先登录，也不自动切换模型服务商。         |
| `lmm login`           | 登录或切换 CLI 账号；应用账号变更需要另行确认。              |
| `lmm logout`          | 退出 CLI，明确展示仍有效的应用授权。                    |
| `lmm status [软件]`     | 查看安装、管理关系、接入和最近验证状态，不触发付费调用。            |
| `lmm sync [软件]`       | 更新 LMM 模型和接入信息，不擅自切换服务商或默认模型。           |
| `lmm update [软件]`     | 检查并确认更新；`--all` 只包含已授权纳入管理的对象。          |
| `lmm doctor [软件]`     | 检查问题；增加 `--fix` 后执行允许的修复。               |
| `lmm restore [软件]`    | 选择并撤销 LMM 的配置变更，保留无关内容和用户后续修改。          |
| `lmm disconnect <软件>` | 解除指定软件或实例的 LMM 接入，处理其应用授权。              |
| `lmm uninstall <软件>`  | 确认后卸载指定软件，默认保留数据和共享依赖。                  |
| `lmm run <软件>`        | 按当前有效配置启动；未安装时，确认后完成安装和接入。              |

涉及多个实例的命令都应允许指定实例。未能唯一确定目标时，不得默认操作全部实例。

用户完成接入后，也应能通过原软件的命令或图标启动，不强制要求始终使用 `lmm run`。

## 十三、验收标准

| 场景           | 通过条件                                                |
| ------------ | --------------------------------------------------- |
| 全新设备         | 通过一次 `setup` 完成所选软件的安装、授权、配置和实际调用验证，无需手动填写模型服务配置。   |
| 仅安装软件        | 未登录 LMM 也能完成安装，不产生模型授权或付费调用。                        |
| 已有其他服务商      | 能添加 LMM，并按用户选择决定是否启用；原服务商和无关配置保持不变。                 |
| 多环境、多实例      | 只修改明确选定的环境和实例，其他环境、项目和用户配置不受影响。                     |
| AstrBot 接入   | 指定实例和目标配置实际通过 LMM 完成调用；原有机器人设置及数据保留，不向真实聊天对象发送测试消息。 |
| CC Switch 共存 | 普通切换和本地路由场景均能准确识别状态；用户切换离开 LMM 后，不被同步或修复强行切回。       |
| 能力验证         | 简单文本成功但必要的工具调用或流式输出失败时，不标记对应编程场景完整可用。               |
| 费用与额度        | 未授权不进行付费测试；测试遵守已确认限制，余额不足不自动充值或换用其他收费方案。            |
| 授权撤销         | 只影响选定应用或实例；撤销确认后，不再接受使用该授权发起的新调用，已开始的调用与费用另行说明。     |
| 重复执行         | 同一目标连续执行三次 `setup`，不产生重复软件、服务商、插件或多余授权。             |
| 中断与部分失败      | 再次执行能够继续；单个目标失败不破坏其他成功项，未完成内容有明确说明。                 |
| 并发修改         | 用户或 CC Switch 在执行期间修改同一设置时，LMM 不覆盖最新内容，而是停止冲突操作并提示。 |
| 更新与恢复        | 更新后重新检查接入；恢复不会丢失用户后续修改，也不会重新激活已撤销授权。                |
| 状态真实性        | 未检查、未启用、等待操作、历史验证通过和当前故障均可区分，不以笼统“成功”掩盖差异。          |
| 隐私与卸载        | 可分享报告不泄露凭据；解除接入和卸载不误删用户数据，并清楚交代剩余授权与运行依赖。           |

**最终交付：用户可以放心安装、实际使用、持续维护，并随时退出的 LMM 接入环境。**
