# DP-26 研究报告

日期：2026-10-10。基线：`72667564c0431754d4856dc2e0db55f360bd2745`。
结论：**组件 CPU/分配优化成立；并非所有负载都降低常驻内存。完整 1c1g、真实资金与更新验收未完成。**

## 1. 先核对实际接线

Rust 公共 HTTP 路由在指定基线只让 `/health/live` 成功；就绪页和模型路径返回 503。Go 宿主只注册身份模块，工具市场没有在该入口启用。[S1][S2]

本补丁作用于工具市场以后接入时的 MCP 结果解析；**它不会让当前身份宿主直接省下报告中的资源，也不会让尚未启用的模型路径获得服务能力**。代码中存在账本和转发组件，不等于公共请求已经经过两者。没有向生产模型接口发请求，也没有用健康页吞吐替代业务吞吐。

Go 宿主已有每模块 8 个在途请求的本地限制，满载时立即拒绝。但它不构成跨节点配额，更不能充当资金权威。[S2] 本次没有扩展或绕过这些权限。

## 2. 最小补丁与正确性

原 SSE 路径执行 `uniqueJSON → json.Unmarshal → rpcResult`；最后一个函数又重复前两步。候选复用已经检查过的 `rpcEnvelope`，通过同一个结果检查函数返回 `json.RawMessage`。普通 JSON 路径仍执行完整的原始输入检查。[S3]

没有删除重复字段/嵌套深度检查、版本检查、请求 ID 精确匹配、错误和空结果拒绝。没有新增共享缓存、字符串驻留或缓冲池。没有改动网络规则、TLS、身份、资金、审计、自动重试、响应体关闭或生命周期。

基线与候选各运行 3 次同一套检查：20 类 JSON/SSE 响应，8 类流边界，4 类错误状态，以及取消、关闭响应体、32 路不同用户测试结果隔离和返回缓冲独立性。各次通过。`9007199254740993` 的响应原文被保留；**这是协议原文测试，不是金额结算或账本守恒证明**。另有固定 50 次操作的分配微测试；其耗时不能转换成服务容量。

没有运行完整项目测试、项目级竞争检测、Rust 编译或真实 PostgreSQL 账本验收。原因是本地没有完整仓库和 Rust 工具链，Go 1.23.2 也低于项目的 Go 1.25 最低要求。[S4] 试验使用实际源码提取件，不把替身写成完整服务。

## 3. 方法与边界

三个基线文件 `mcp.go`、`schema.go`、`network.go` 的 Git 对象哈希已逐一核对；`results/provenance.json` 保存对象哈希、完整起点和二进制 SHA-256。构建固定 `CGO_ENABLED=0`、`-trimpath`，性能测试不启用竞争检测。基线/候选交替顺序为 A/B、B/A、A/B。

被测进程同时包含实际解析代码、本地 TLS 测试服务和负载驱动。CPU 和分配数据包含三者，**不是纯服务开销**。TLS 证书检查保持启用，服务令牌只用测试值。每次结果核对 SHA-256、精确大整数、调用次数、错误数及最后的在途数。没有模型生成、Rust 用户身份服务、数据库或资金结算。

负载是一个 MCP 结果事件，不是逐 token 的公共模型流；正文使用重复 ASCII 字符，不能代表复杂 JSON 或混合模型请求。首字节从实际 HTTP 调用计时，总延迟从计划到达时刻计时，包含驱动调度滞后；首字节不是首个模型 token。标准组 64 KiB、每秒 60 次、120 次请求；另外测 4 KiB、512 KiB、大输入、慢读取、普通 JSON，以及 80 次/秒的慢读取并发组。并发组实际达到 4 条在途请求，不是仅把并发参数写成 4。每个有负载的常规窗口约 2 秒，含独立空闲、8 次预热及完成后观察；**这些短窗口不能证明长期稳定、泄漏不存在或容量上限**。

总计 81 个完整运行记录、87 个进程运行、7,560 次测量阶段成功调用，失败与驱动拒绝均为 0；预热和微测试不加入该成功数。另有 1 次外层命令超时：内部报告 120 次成功，但缺少完整外层采样，单独保留日志并重跑，不混入三次完整对照。全部数据见证据包；三次原值与范围见 `results/summary.json` 和 `results/TABLES.md`。

本机允许 5 个逻辑 CPU，外层共享容器 CPU 配额为 4 核、内存上限 4 GiB。研究子进程固定一个 CPU，但不是独享核，也没有独立 1 GiB 容器。控制目录只读；没有修改宿主机、交换空间或压缩内存。2 GiB 虚拟地址上限和 512 MiB 常驻内存监控**不等于** 1c1g。共享容器的总占用和文件缓存单独记录，不能归属给本试验。[S6]

| 64 KiB SSE | 2.276 → 1.470 | 1264.535 → 872.523 | 12.352 → 11.969 | CPU −35.43%，分配 −31.00%，PSS −3.10% |

| 64 KiB、4 条在途 | 2.404 → 1.733 | 1271.934 → 879.912 | 12.641 → 12.547 | CPU −27.90%，分配 −30.82%；并非每流内存上界 |
| 256 KiB 输入、64 KiB 输出 | 4.855 → 4.290 | 2941.708 → 2558.781 | 13.020 → 12.773 | 总延迟 p99 略升；首字节更慢 |

标准 SSE 组 CPU 毫秒/成功范围：原 2.262–2.781，新 1.359–1.505。总延迟 p99：原 4.163 ms（3.670–15.307），新 2.911 ms（2.527–3.911）。首字节 p99：原 0.693 ms（0.542–1.155），新 0.600 ms（0.371–0.605）。固定发送速率下两者都完成约 60 次/秒，**不能把 CPU 节省换算成已证明的吞吐提升**。

大输入组的总延迟 p99 为 5.819 → 5.851 ms，首字节 p99 为 3.569 → 4.874 ms；512 KiB 组首字节也变慢。小结果及并发组的首字节中位数同样略升。保留这些回退，不用平均延迟掩盖。小样本的 p99，尤其 16/24 次调用的组，只是描述值，不是稳定尾延迟承诺。

512 KiB 结果的常驻内存上升原因尚未被独立验证；不能仅凭分配减少推定峰值会下降。性能分析中重复解析相关分配减少，与补丁机制一致，但不足以证明所有内存变化的成因。

## 5. 双进程重叠不等于完整更新

同一 CPU 上保持总发送速率 60 次/秒，分别运行两个旧二进制，或旧二进制加候选二进制，各 3 次。旧旧组近同时采样 PSS 合计峰值：18.297 MiB（18.133–18.355）；旧新组：24.223 MiB（24.215–24.312）。**混合版本约多 32.39%**，不是更新内存优化。

旧旧组两进程能共享约 6,400 KiB 的只读映射；旧新组对应共享只读页记录降至约 4 KiB。此观测解释了为什么不能拿两个相同二进制的成绩估算新旧版本成本，但仍不是生产镜像的固定开销。原始 `Shared_Clean`、PSS 和 RSS 记录保留在证据包。

旧旧组负载阶段 CPU 合计中位数 0.319 秒，旧新组 0.281 秒；后者最差一轮 0.422 秒，高于旧旧组最差 0.328 秒。没有据此承诺更新 CPU 收益。

本试验不包含镜像下载、解包、真正启动注册、入口切流、在途资金结算、进程崩溃恢复或数据库。因此每次真实更新的成本、最长间隔和恢复时间仍未测得。生命周期文件未修改；交接任务 22/23 见 HANDOFF.md。

## 6. 参数与观察工具

Go 组件默认试验参数为 `GOMEMLIMIT=96MiB`、`GOGC=100`、`GOMAXPROCS=1`；这只是研究参数，不是已批准的服务默认值。

`GOGC=50` 的三次观测：PSS 下降约 15.60%，CPU/成功上升约 24.45%，总延迟 p99 上升约 29.30%。`GOMAXPROCS=2` 在固定单 CPU 时没有收益，CPU/成功和尾延迟都上升。`GOMEMLIMIT=64MiB` 基本不影响常驻内存；这份轻负载未证明内存限制受到压力，不能把未触及的软上限当成节省。[S5]

参数组只改变一个配置，各有三次记录，但与默认组不是相邻配对，存在时间段差异。以上仅用于筛除没有明显价值的方向，不据此改部署配置。

外部 20 ms 采样器在标准组每次约耗 0.047–0.052 CPU 秒，关闭采样时外层运行器约 0.009–0.012 秒。记录的是外层进程 CPU，不含在被测进程 CPU/成功内。移除采样后被测进程没有总是更快，说明短窗口噪声不可忽略；没有做“减去开销”式修正。

CPU 和分配分析各有 3 次基线/候选对照。标准候选 CPU/成功中位数由 1.470 ms 变为 CPU 采样组 1.619 ms、分配采样组 1.511 ms；这些组不混入主成绩。CPU 采样停止阶段的 CPU 被计入，而 `elapsed_seconds` 是负载窗口；不能拿该组利用率推容量。分配分析文件有采样误差并包含启动/预热历史，只用于定位，不代替 `TotalAlloc` 增量。

## 7. 内存字段如何读

`VmSize` 是虚拟地址空间，本次可超过 1 GiB，但不是已经使用了 1 GiB RAM。`VmRSS` 是进程常驻页；`Pss` 按共享者分摊页面。`RssFile` 是驻留的文件映射，不等于容器的全部文件缓存。读取 `Shared_Clean/Dirty` 和 `Private_Clean/Dirty` 辅助解释共享情况。

Go 分配量是累计分配，不是同时存活的内存；`Sys-HeapReleased` 只反映 Go 运行时负责的内存。[S5] 容器应另外测 `memory.current/peak/stat`、交换页和内存压力；这些值可能包含网络缓冲、文件缓存和内核开销。[S6] 本环境的共享容器数据只作环境记录，专属服务容器占用记为未测。

20 ms 采样可能错过很短的峰值，预热阶段有些轮没有采样点，保留 null。不把各阶段最大值相加，不把两个不同时刻的进程峰值相加。记录的更新 PSS 合计使用近同时观测，不是独立峰值之和。
