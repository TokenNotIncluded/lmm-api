## 一处控制入口，按任务调用接口

以下是 DP-29 提出的适配契约，**不是已存在的 Rust/Go RPC 名称**。在接入其他研究分支时，应在这一层转换其实际接口，不要求每个任务另建完整部署器。

| 适配器名称 | 调用动作 | 提供方责任 |
| --- | --- | --- |
| `dp24` | `inspect`、`fence` | 返回经过身份验证的节点、组件和旧页面能力；持久保存执行代号；为其他适配器提供同一份节点操作记录。 |
| `dp28` | `space` | 检查下载、展开、旧产物、回退保留、日志和内存峰值；容量不足返回等待，不能删除仍被引用的内容。 |
| `dp27` | `pull` | 获取预编译产物、校验摘要和来源，确认架构与配置；不在服务节点执行源码构建。 |
| `dp22` | Rust 的 `prepare` 到 `finish` | 调用核心生命周期和稳定入口；就绪后接新流量，旧流与结算完成后退出。 |
| `dp23` | Go 的 `prepare` 到 `finish` | 调用扩展生命周期；工作租约、重复任务和副作用恢复必须由扩展自身保证。 |
| `frontend` | 前端的 `prepare` 到 `finish` | 最终统一入口的前端接线槽位；保留旧资源和旧页面 API，不能清会话或强制刷新。当前没有真实实现。 |

`hooks.py` 只按上表调用一个本地可执行文件。库存明确给出其绝对路径和 SHA-256；缺失或摘要不符时拒绝。JSON 经标准输入输出传递；不拼接 shell，不传入当前环境中的数据库密码或服务密钥。输入输出均限制为 64 KiB，单次调用最长 5 秒。

长操作须提交后立即返回操作状态，再由后续调用查询，不能在适配器里等待长流结束。超时后只终止适配器进程组，并保留控制端意图。**服务进程必须由 Docker 等服务运行环境独立管理，不能留在适配器进程组中。** 未验证此边界的适配器不得接入。

本地可执行文件及库存属于受信任运维配置。`environment: isolated` 是防误操作声明，不是操作系统隔离或生产网络封锁。示例没有远端目标、真实凭证或可用适配器，不能据此宣称已具备双向 TLS。

## 请求与返回

动作请求包含 `api`、`authority`、`cluster`、`release_id`、`epoch`、`operation_id`、`plan_digest`、`node`、`direction`、`action`、目标/先前产物清单和策略。`operation_id` 为除自身字段外请求规范 JSON 的 SHA-256。

`inspect` 是只读请求，返回节点身份、环境、架构、当前新架构 schema 版本、出现过的业务状态、各组件正在接流量的清单及共存版本、仍需兼容的旧页面清单。跨机实现必须绑定到 DP-24 的服务身份，不能信任网络上任意 JSON。

动作返回必须绑定同一个 `api`、`operation_id` 和 `epoch`。`status` 只能为 `ok`、`wait`、`failed` 或 `rejected`。未知状态、损坏结果或缺少操作绑定都不是成功。控制端保留未确认操作，等待同一 ID 的核对。

`ok` 还必须携带所需证据：

| 动作 | 必要证据或节点保证 |
| --- | --- |
| `fence` | 节点持久接受该控制端和执行代号；所有生命周期适配器共用此记录。 |
| `space` | 容量检查及保留政策已经执行。准备实际实例时再次检查，避免预检后资源被占用。 |
| `pull` | `verified: true` 和实际校验的 `artifact_digest`；真实发布还需 DP-27 验证来源。 |
| `ready`、`switch` | 实际产物摘要、配置摘要、已启用能力及 `business_ready: true`。健康页或仅启动成功不足以满足。 |
| `observe` | 满足样本数和观察时长，明确资金结果。`pending` 等待，未知资金状态阻塞。 |
| `drain`、`finish` | 旧实例的 `inflight` 和 `unsettled` 均为整数 0；不能用超时强制归零。 |

`failed` 是已经确定的业务失败，可触发兼容性检查后的自动应用回退；`rejected` 是确定拒绝，停止推进。通信中断不能伪装为这两种确定结果。资金未知结果不能由发布控制器重放或补算。

节点必须先检查执行代号，再查已有收据。更旧代号一律拒绝；同代号不能换发布 ID。执行产生实际副作用和记录结果之间发生崩溃时，适配器必须通过确定的实例名、路由版本和操作 ID 核对实际状态。模拟节点用同一 SQLite 事务完成此事；这**不能证明**真实 Docker 操作和路由变更具有原子提交能力。

## 控制状态和调度

计划创建时获得不可变 ID、清单摘要和 `revision=1`。创建后不能修改原计划正文；修改需求生成新计划。预检读取全体节点，检查旧/新组件共存、配置、协议、架构、当前数据和旧浏览器接口。一个控制状态库同一时刻只允许一个活动计划。

开始计划或切换回退方向时，递增全局 `epoch`。取得全部节点的确认后，依次执行目标组的每个节点。一次最多更新一个节点，最多两个同组件运行版本。本版不并行执行多个节点的更新；这是明示的资源与恢复策略，不是更大并行数的性能结论。

每一步先保存 `pending`，提交控制状态，再调用适配器。控制器在节点提交后退出，恢复时重用同一 ID。正常完成后清除 `pending`、递增执行版本号。所有本地变更在同一文件锁内进行，SQLite 事务保持状态和活动计划指针一致。

`gc` 只清理明确结束的控制历史。它保留最新回退记录、运行中或结果未知的计划，采用期望 `epoch` 防止旧清理命令误用。SQLite 可复用已释放页，不自动执行需要额外大空间的 `VACUUM`。

控制器不提供自动多主选举或状态库丢失后的无状态接管。状态丢失时停止发布，已运行服务继续处理请求。恢复控制状态、节点身份和执行代号需要受控运维流程，不能初始化一个空库后强行覆盖旧节点。

## 数据和前端

清单包含新架构 schema 的读写范围。普通启动只读取控制库版本，不升级控制表；控制器没有业务建表、迁移、恢复快照或余额改写动作。业务 schema 的未来升级由单独受控流程进行。

回退前重新读取当前 schema、状态和实际部署。旧版本不能读取当前数据时拒绝回退，保留现状等待前向修复。更晚发布过同样的产物，也不能让旧发布记录重新取得回退权。

前端保留两份不同信息：资源文件引用，以及浏览器仍可能使用的 API 契约。旧前端实例退出不删除这两类引用。未来 DP-28 须给出有界保留与释放证明；缺少这类证明时不能承诺无限高频前端发布或无限磁盘安全。

## 还必须完成的联合验收

真实适配器目前全部缺失。接入后必须用实际 Rust/Go 进程、真实新架构 PostgreSQL 和受限容器，重新验证切流时序、任务恢复、资金结算、控制器突然死亡、网络分区及节点身份轮换。

`evidence/compatibility-matrix.json` 的 256 组结果是清单规则计算：三组件版本的 8 种选择 × 三组件独立配置的 8 种选择 × Rust/Go 协议发送版本的 4 种选择。示例假设读写范围兼容；负例在自动测试中。它不是 N/N+1 原生程序互通测试，也不验证实际 Protobuf 枚举处理。

未测 Docker、真实双向 TLS、数据库持久化故障、完整模型/支付链路、生产浏览器页面、真实 3/5 服务器、1c1g 持续容量和全节点磁盘总占用。不能据本原型宣称可生产发布或给出实际最短更新间隔。
