## 2. 连接预算与更新重叠

直接连接的公式为：

```text
应用峰值 = Σ〔每个物理池的最大连接数 ×（稳定实例数 + 同时额外存活实例数）〕
所需总额 = 应用峰值 + 一次性管理/恢复/备份连接 + 预留名额
```

同一个 PostgreSQL 实例上的所有数据库、角色、节点和新旧版本都要加入预算。以下仅计算当前已接线的身份 HTTP + RPC，每实例 8+2=10，不含额外管理进程。

| 核心节点数 | 稳态配置上限 | 一次只多开一个实例 | 全部旧新实例同时存在 |
|---:|---:|---:|---:|
| 1 | 10 | 20 | 20 |
| 3 | 30 | 40 | 60 |
| 5 | 50 | 60 | 100 |

这些数值是源码推算，不是实际连接峰值。账务、事件和未注册 Go 模块接入后，必须重新计算。

本研究给实验配置保留 3 个超级用户名额、2 个恢复角色名额，并在容量清单中另留 1 个运维名额，总共 6 个，普通业务预算为 26。前两类由 PostgreSQL 参数和角色权限提供保护；最后 1 个是计划中的余量，不是另一个数据库参数。应用角色不能拥有超级用户或保留槽权限。现有开发 Compose 的单一数据库角色不算完成保护验证。[PG17 连接设置](https://www.postgresql.org/docs/17/runtime-config-connection.html)、[当前开发部署说明](https://github.com/TokenNotIncluded/api.lmm.best/blob/72667564c0431754d4856dc2e0db55f360bd2745/deployment/docker/README.md)

按此候选预留，单核心滚动更新为 20+6=26，算术上可容纳；若再运行一个最大池为 8 的管理进程，则为 34，应拒绝同时执行。三核心稳态已经是 30+6=36，不能保证在 32 连接上限内。不能用“大多数连接闲置”消除峰值风险。

生产连接策略尚未改动。建议先实现并核验统一池配置、限时取连接、有限排队和全局更新准入，再考虑降低每实例池上限或引入事务池。降低默认值会影响延迟，不能未经实测把任意小数字写成最佳配置。HTTP、RPC、资金和事件可有独立业务名额，但不能为了复用而合并不同权限角色。

释放连接与排空流请求不同：长模型流不应占住数据库事务直到输出结束。持久结算应是有界事务；连接取不到时拒绝或进入已设计的恢复路径，不能重新访问上游或换一个扣款请求号。

`budget.py` 仅实现计算与阻止超预算清单；没有修改运行时池大小，也没有自动协调发布锁。交给 DP-29 的是预算字段、阻止条件和管理任务互斥要求，不是已完成的发布控制器。

## 3. 256 MiB 参数与内存计算

[现有示例](https://github.com/TokenNotIncluded/api.lmm.best/blob/72667564c0431754d4856dc2e0db55f360bd2745/deployment/docker/compose.identity.yml) 只有 256m、32 个连接、64MB shared_buffers 等开发设置。它没有证明热点写入、检查点、备份和版本重叠的联合峰值。

实验候选保持 shared_buffers=64MB，设置 work_mem=1MB、hash_mem_multiplier=2、maintenance_work_mem=16MB、autovacuum_work_mem=8MB，限制一个 autovacuum 工作进程及关闭并行查询工作进程。它保留 fsync、full_page_writes、同步资金确认。详细设置在 `postgresql.conf`，未用于生产。

work_mem 不是全库总内存上限。一个查询可以同时拥有多个排序和哈希操作，多个会话和并行工作进程会继续叠加。[PG17 内存配置](https://www.postgresql.org/docs/17/runtime-config-resource.html)

例如明确假设 8 个会话，各有 2 个排序和 1 个哈希操作，没有并行工作进程，操作预算为 `1MiB × 8 × (2 + 1×2) = 32MiB`。这不是数据库只需 32MiB，也不是总峰值。仍须记录后端私有内存、共享缓存、WAL 缓冲、临时缓冲、维护并发、计划缓存、文件缓存和探针成本。维护参数也按实际并发工作计算，不只加一次就结束。

实验采集 cgroup 总占用与峰值、memory.stat、memory.events、CPU/IO 计数、PSS 和 PG 原生视图。共享页不能把各进程 RSS 直接相加。PSS 和 cgroup 总占用也不能相互替代。镜像拉取、构建、负载发生器和恢复实例不包含在数据库容器的 256MiB 中，应另计到整机和集群预算。

本轮没有任何有效数据库内存、IO、延迟或吞吐样本。候选参数合格与否仍未确定。`max_wal_size` 不是严格磁盘上限；本任务不删除 WAL，也不把复制槽限制等同于完整磁盘生命周期方案，相关后续归 DP-28。

## 4. 直接连接与 PgBouncer

结论是：**目前不能直接把现有 DSN 换成事务池地址。** 源码的三个连接构造器都在 after_connect 中执行会话级 SET。RPC 尤其依靠会话设置只读；其当前 DSN 与 HTTP 共用。事务结束换后端时，不能假定这些设置仍随逻辑连接保留，也不能把“只读会话设置”当数据库写权限隔离。

| 项目 | 实际线索或缺口 | 采用事务池的条件 |
|---|---|---|
| 会话 SET/RESET | 身份、RPC、事件池存在 | 改为经验证的角色默认设置或事务内设置；同时用角色授权限制写入 |
| SET LOCAL、事务锁、行锁 | 账本和 charging 存在 | 必须在同一完整事务内；重试不携带上一事务会话假设 |
| SQLx 预处理 | 当前实际驱动未运行 | 用选定版本与真实驱动验证协议级预处理、重复执行、连接轮换与失效恢复 |
| SQL PREPARE / DEALLOCATE | 未完成全库扫描 | 不可把它与协议级预处理混为一谈 |
| 临时表 | 未完成全库扫描 | 区分 ON COMMIT DROP 与保留跨事务内容；后者走独立会话 |
| LISTEN/NOTIFY | 未完成全库扫描 | LISTEN 需保留专用会话预算；NOTIFY 不替代持久事件与重放 |
| 会话锁 | 未完成全库扫描 | 会话级 advisory lock 不直接迁入事务池 |

PgBouncer 官方功能说明区分上述能力；协议级预处理支持需要非零 `max_prepared_statements`。它不是“所有 prepared statement 均兼容”的结论。[功能说明](https://www.pgbouncer.org/features.html)、[配置](https://www.pgbouncer.org/config.html)

会话池可以作为兼容性对照，但应用长持有连接时，不应期待它像事务池一样压缩后端连接数。两种方式都需要测量延迟、错误率、排队和故障重连，当前没有胜出者。

PgBouncer 的数据库连接预算需按每个代理实例、数据库、登录角色分别计算普通池和 reserve_pool_size，再加入代理新旧版本重叠。max_client_conn 不是 PostgreSQL 后端连接总上限。不要每个应用节点都新增独立代理、每个角色给一个大池后，仍只计算单个代理。不能用强制统一登录用户的方式消除核心/扩展权限隔离。`budget.py` 已加入这种逐池计算，但未启动 PgBouncer。

## 5. 共置、单库与高可用边界

低负载共置可减少专用节点数量，但数据库与应用共享 CPU、内存、文件缓存和磁盘，更新时新旧应用重叠也必须算进去。独立数据库节点把应用更新与数据库资源争用分开，却不消除单点。这里是故障边界分析，没有实测成本或性能胜出结论。

所有 Rust 核心必须指向同一个资金写入权威。禁止每个应用节点初始化各自的权威余额库。Go 的扩展数据可以与核心放在同一 PostgreSQL 实例的独立数据库/角色中，但实例连接预算仍合计。它只隔离数据权限，不隔离实例崩溃与存储故障。

| 方案 | 已确认写入可能丢失多少 | 本轮恢复证据 |
|---|---|---|
| 单主库，数据库进程崩溃但有效数据盘保留 | 在正确同步确认和可靠存储前提下，设计目标是不丢失已确认提交；不是本轮测得的零丢失 | 未测；实验代码比较崩溃前后真实账本 |
| 单主库，整盘丢失，独立备份可用 | 最近已在独立位置可靠保存的备份/WAL 之后的写入可能丢失；目前没有量化边界 | 未测；本代码逻辑备份保存在同机，不覆盖此故障 |
| 异步副本接管 | 未到达副本的已确认写入可能丢失，不能只因“有副本”就声称零丢失 | 未测，不作为降低资金确认要求的优化方案 |
| 同步副本、已验证旧主隔离、合格副本接管 | 仅在已确认日志被接管副本持久保存、隔离正确等明确故障模型内，才能讨论不丢已确认写入 | 未测，没有搭建自动接管系统 |

同步复制确认的范围取决于 synchronous_standby_names 和 synchronous_commit 等设置；本候选实验没有同步副本，`synchronous_commit=on` 在这里保证的是本地主库的确认要求，不能直接推导异机持久化。[PG17 热备与同步复制](https://www.postgresql.org/docs/17/warm-standby.html)

高可用方案必须先确定唯一写入者。将旧主从负载均衡中摘除、探测不通或租约到期，不自动证明旧主已经不能继续接收资金写入。切换前需要可靠断电、存储访问隔离，或能证明旧主写路径会自行停止的机制。隔离没有成功证明时，不提升新写主；不能在恢复服务压力下允许两个主同时写钱。[PG17 故障切换](https://www.postgresql.org/docs/17/warm-standby-failover.html)

同步副本丢失或网络分区时，不能静默改成异步资金确认来保持数字好看。测试需分别隔离旧主、阻断复制、阻断控制通信、恢复旧主，并用同一操作号在两边尝试写入。必须证明至多一个有效写入者；本轮没有这项证据。

副本与独立备份解决不同故障。误删和错误业务写入可能复制到副本；独立保留的备份及连续 WAL 归档还要实际恢复验证。[PG17 连续归档与恢复](https://www.postgresql.org/docs/17/continuous-archiving.html)

恢复时间必须分解记录：发现故障、隔离旧主、选择副本、提升、切换入口、应用重连、恢复未知提交、资金核对。当前这些测量全部为空，不承诺 30 秒或任何数值。单机容器重启的时间也不能当作整套 HA 的恢复时间。

## 6. 恢复与资金守恒验收方式

隔离实验使用原始 identity/ledger SQL 和真实 `post_ledger` 函数。没有使用测试替身余额表。已写入但未完成数据库运行的检查如下。

- 每笔分录合计为零；所有余额合计为零；余额状态与历史分录/修订号一致；非清算账户不为负。
- 单账号热点的预留、部分结算，以及未消费部分退回。每次完整迭代恰好新增两笔请求/账本记录，结束后没有残留预留。
- 原请求重放不改变账本；同一操作号改参数必须拒绝；恢复后的重复充值不能再增加余额。
- 在 COMMIT 确认帧处断开客户端。先从权威主库查询请求与存储结果，再用同一操作号、同一参数重试；确认没有重复收费。
- 已确认账本在保留数据盘的进程崩溃后保持一致；逻辑备份恢复到另一新卷、新实例后，余额、历史摘要和去重结果一致。

未知提交不是简单失败。错误返回后不能换操作号或再次访问上游来“补做”。从只读副本查不到记录也不能当作没有提交；原事务仍可能进行，副本也可能滞后。重试必须在唯一权威写主上按原请求进行，并由数据库去重/锁决定结果。源码已定义相应错误边界，但真实 Rust 连接池重连和调用方行为仍未验证。

本代码的 COMMIT 截断工具已通过帧级测试，尚未和 PostgreSQL 配合运行。数据库进程崩溃测试安排在已确认负载之后，不覆盖每个业务阶段的进程死亡、磁盘断电或任意写入中断。

备份恢复到更早时点可能同时丢失后续去重记录。余额历史在备份时点自洽，不足以证明外部支付、模型消费与本地状态一致。需要保留并核对外部支付凭据、已确认操作清单和事件恢复结果；尚未进行这类联合验收。
