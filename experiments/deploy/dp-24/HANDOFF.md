# DP-24 接入方案与协议交接

**本文件的接入步骤是设计，除明确标注的 Go 校验模块与本机试验外，均未完成生产代码接入。**
不修改已有 Protobuf 字段编号、字段意义或金额单位。交接对象为 #675 的协议与资金实现。

## 1. 同机与跨机的选择

同机配对继续用私有 Unix socket。优点是没有证书握手、进程数不增加；缺点是核心与扩展的部署位置受配对限制。
跨机选原生 gRPC 双向 TLS。双方验证专用 CA、用途、名称及服务身份，禁止明文 TCP、系统根的隐式回退和跳过名称验证。
先不加独立代理进程。本轮没有证明代理有性能或内存收益；代理还会增加升级对象和身份传递边界。
保留 Docker，构建产物与部署方式不由此任务改变。

Rust 最小接入点是现有 `RpcServer` 的可选 TLS 监听方式与服务授权入口。默认仍为 UDS。
在接受 TCP 连接及执行 TLS 握手前取得连接名额；握手设期限；断开、超时或失败立即归还名额。
不能只限制 HTTP/2 已建立连接中的调用数，而让未完成握手无限累积。
Go 最小接入点是 `coreclient.New` 的显式传输配置，复用现有调用包装、元数据覆盖、消息边界与调用期限。
不要通过通用 URL 自动决定是否使用明文。

## 2. 三层权限分别处理

第一层是 TLS 连接身份：服务节点自己的叶证书，专用 CA；节点名与 IP 分离。
第二层是服务权限：把证书中的固定服务 URI 映射到允许的方法集合；未知方法默认拒绝。
第三层是用户权限：继续使用 `x-lmm-user-credential` 由 Rust 查当前权威数据。
通过前两层不能省略第三层，更不能省略资金事务内的权限和余额检查。

Go 不持有核心数据库地址、密码、私钥或数据库网络访问权。扩展自有数据库应使用独立账号。
已授权的 TLS 客户端也不能任意选取另一个服务的事件订阅或资金回执。
保留事件服务的服务器侧订阅主体绑定；不能信任请求中自报的服务 ID。
不要让每个节点共享同一份长期私钥，否则无法单独撤销受损节点。

Go `transportpolicy` 已实现专用根、TLS 1.3、HTTP/2、名称验证、确切服务 URI、完整叶证书摘要和有限期策略检查。
它不是完整 SPIFFE 身份发行系统，也不实现服务端方法权限、签名配置下发或数据库授权。

## 3. 稳定地址、发现和连接复用

建议由受信任的部署控制端原子写入一个有版本的节点清单：节点 ID、连接地址、验证名称、证书摘要、服务 URI、协议主版本、到期时间。
不从用户输入或未经验证的 RPC 响应接受节点清单。DNS/IP 只负责找地址，不授予身份。
新地址与证书身份分开校验：例如地址改变后仍必须验证原定名称，而非把收到的名称当成可信名称。

第一版最多 8 个候选节点，不引入新的发现守护进程。
建议每个扩展进程只保留 2 条活动连接，轮换时最多再保留 2 条停止接入的旧连接；达到上限即拒绝创建更多连接。
允许证书项的 8 项上限包括新旧两代；因此大量节点不能同时保留两代证书，应分批轮换，不能静默突破上限。
这是待实测的设计数值，不是当前代码保证。多扩展进程的总连接数必须同时符合每台核心的 8 连接预算。
一条长连接复用多个有上限的调用，不为每次请求重新做 TLS 握手。

发现改变只影响新调用。先核验新节点身份与协议，再把新调用切入；旧流继续绑定旧节点。
旧节点断网或死亡时，在途流结束为失败或未知结果；禁止无声地另起一个计费模型请求来续流。

## 4. 轮换、撤销与配置失联

建议服务策略有效期不超过 60 秒，正常每 20 秒刷新。
叶证书更新顺序：发布新旧证书的有限允许窗口 → 建立新连接并核验 → 切新调用 → 停止旧连接接入 → 到期或显式撤销旧证书。
本次 Go 模块强制策略租期不超过 60 秒，最多 8 个允许证书项；每份证书有自己的截止时间。
这只是可验证的默认研究边界，刷新机制尚未实现。

必须在**每个新 RPC**再次校验策略和证书时效，不能把一次握手成功当作永久授权。
Go 模块只提供校验函数，调用方仍必须保证每条复用连接上的每次调用都经过它。
服务端也要做同样的调用级复核；仅在客户端检查不能阻止持有旧客户端的调用方。
长时间订阅流要有单独的最大流时长或周期复核；新调用拒绝不能代替既有长流撤销。

策略文件无效、过期、回退或读不到时，停止新调用，不无限保留旧策略。
普通升级可让已接受的、有上限的工作完成；安全事件中的显式撤销应立即阻止新副作用，并终止受影响的长流。
已经提交的资金记录不能因撤销而回滚成“从未发生”；以同一操作 ID 查询和补结算。

`Store` 只保存进程内最高版本。接入时必须先持久化最高版本，再接流量，避免重启后接受旧配置。
还需以单调时间限制策略在本机的使用年龄，检测墙上时钟回拨；当前模块没有实现此保护。
60 秒不是网络分区下的“即时撤销”承诺：未收到撤销的节点最多继续使用未过期服务策略，到期必须拒绝。
用户消费授权另走当前数据库检查，不能沿用这 60 秒服务策略作为用户许可缓存。
根 CA 轮换需双根有限重叠、明确删除旧根、关闭旧代连接并重验；本轮未完成该实现或试验。

## 5. 会话与资金不能跟着实例漂移

现有会话/API Key 是数据库保存摘要的随机凭据。扩容时复用同一权威身份库，不重发用户凭据，不按实例重建另一套随机签名密钥。
不得把异步只读副本或本机旧缓存作为消费授权来源。权威库不可达时停止新消费。
授权结果中的付款账户只是候选项；真实资金事务仍需重验账户、成员关系、版本、预算与金额。
撤销与消费并发时，需要由事务锁或明确的版本约束确定先后，不能把早先 RPC 的成功当成永久许可。

资金命令在第一次发送前，先把原始操作 ID 和完整请求内容写入扩展自己的持久任务记录。
超时、断线或换节点后不生成新 ID；先查询该 ID 的原结果，未知状态保持待核对。
同 ID、不同用户/付款方/金额/币种/动作必须冲突；回执查询必须检查其归属和服务用途。
“没有找到”也不能直接推出“尚未发生”：要考虑读副本延迟和正在提交的事务。
只有权威核心能判定能否安全重试同一原命令。

试验中的 `dp24.lab.Probe/Charge` 与 `Receipt` 不是产品接口，禁止生成对应生产 Protobuf。
现有 Go 付款包装存在，但 Rust RPC 服务器未注册 `CorePayments`。必须继续失败，不使用试验服务兜底。
真实注册、回执查询、幂等唯一约束、事务内授权与结算边界交由资金/协议任务接入并联合验证。

## 6. 重试与资源边界

| 调用类型 | 建议策略 | 不允许 |
|---|---|---|
| 只读身份/能力查询 | 总期限内最多 2 次，仅传输不可用时换一个已验证节点；每次重新检查用户权限 | 无限重试、对认证失败换节点绕过 |
| 资金变更、事件确认、工具副作用 | 不做通用自动重试；保留原 ID，查询原结果；按各自协议处理恢复 | 换新 ID 再执行、把超时当未执行 |
| 已输出的模型/事件流 | 固定原实例；显式报告断流，保留原任务和结算标识 | 自动搬迁字节流或重复发起计费请求 |

Rust 现有边界：8 连接、8 并发调用、64 KiB 消息、8192 字节头部设置、2 秒调用期限。
Go 现有边界：32 在途调用、64 KiB 消息、2 秒期限。不要在重试时为每次尝试重新获得完整 2 秒预算。
TLS 握手、节点清单、证书文件、等待队列、保留旧连接和重试次数也都要有独立上限。
未知协议主版本立即拒绝；增加字段可保持同一主版本的兼容语义，但必须使用真实新旧二进制测试。
当前试验只检查拒绝错误主版本和保留消息格式，没有完成真实版本共存验收。

## 7. 合并前必须补齐

先实现并本地编译 Rust TLS 接入与 Go 生成客户端接入，再用真实 PostgreSQL 跑会话撤销、授权失败、回执查询及资金去重。
在支持 `netem` 的隔离主机补延迟和随机丢包；在两台独立测试服务器补故障、发现、根轮换和连接代际清理。
采用 DP-21 的共同资源负载与预算，测峰值内存、握手洪峰和多进程连接总量。
只在这些结果完成后判断是否启用跨机模式。当前补丁不能作为上线批准。
