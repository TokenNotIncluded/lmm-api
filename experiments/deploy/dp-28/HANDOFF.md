# DP-25 / DP-29 交接

本原型已完成本机文件系统规则验证；下列生产接线尚未实现，不能把布尔参数或离线快照当作真实证明。

## 给 25：数据库和事件

通用清理器永不打开数据库或 WAL，更不直接删除其文件。数据库目录、WAL 目录、备份目录应分别报告挂载点、剩余字节、剩余文件节点和恢复余量。不能把另一挂载点的空闲空间相加后批准当前挂载点的更新。

业务增长预算必须覆盖更新和故障恢复窗口内的写入：正常数据、事务日志、积压事件、去重与审计、备份暂存。没有实测增长上限或恢复窗口时，生产容量结论为未知，发布控制不得采用实验默认值放行。

`event_retirement.assess()` 只检查是否提供八项证明：最终效果可靠保存；所有必要消费者可靠确认；无待恢复或争议操作；重放位置越过事件；备份恢复及重放窗口已覆盖；去重唯一性证据继续保留；资金审计及账本关联继续保留；载荷保留期限已到。

这些条件必须由拥有该扩展数据的模块在同一数据库事务或等价一致性边界中检查。禁止直接采信调用者传来的 `true`。只回收符合条件的载荷，保留事件 ID、效果 ID、请求摘要、去重唯一键、账本关联。即使已确认，也不能因短期未访问而删除去重证据。

应联合测试：回收与重放同时发生；确认结果丢失后重试；从更老备份恢复；消费者重新注册；退款/结算仍在处理中。必须证明没有重复入账，且数据库自身的回收、备份与 WAL 保留规则能恢复。本文的六个保护文件只是哨兵，不是 PostgreSQL 或资金测试。

## 给 29：发布清单、保留和排空

不可变版本根至少包含：当前版本、上一已验证版本、在途/排空版本、正在拉取版本、人工或恢复任务固定版本。Docker 使用完整 image ID/内容摘要，不使用可变 `latest` 作为版本身份。Rust、Go、配置、协议和结构版本的兼容组合应归属同一发布清单；本实验只管理一个组件。

每个本机发布、并发拉取、激活和清理操作必须共用锁或同等的排他机制。PID 存在或 TTL 到期都不能单独证明可删除。运行进程持有版本锁；未完成结算、补偿、交付和恢复操作还需控制器持久保留标记。

释放旧版本要证明：停止接入新请求；流已结束；必要结算已可靠保存；恢复队列无该版本依赖；没有进程或容器引用；已有上一已验证且结构兼容的回退版本。控制器失联时继续保留，不自动超时删除。排空版本超过预算时拒绝后续更新，不杀旧实例换空间。

本原型的 `rollback-probe` 会重新校验并启动保留的本机测试程序，核对版本和载荷。它不切真实入口、不恢复数据库结构、不验证 Rust–Go 协议兼容，不能作为产品回滚完成标记。

清理意图在删除前落盘；删除过程绑定路径、设备、文件节点、类型、长度及修改时间；恢复沿用同一意图，遇到替换文件或新增引用则拒绝。完成收据有写失败时返回失败；再次运行完成收据，不假装未发生的删除。

控制状态只保存当前状态和最后一次清理意图/收据，避免发布历史无限堆积。需要长期保存的发布审计应可靠归档并纳入业务账单，不能静默丢弃；不能为轮转该历史而删掉唯一恢复证据。实验目录保留了本次所有实际删除清单，未实现远端归档。

## Docker 适配边界

`docker_plan.py snapshot.json` 只生成离线预览。快照要求完整容器检查结果（含停止容器和其他项目），完整镜像检查结果，以及 `release_images` 的五组引用：`current`、`previous_verified`、`inflight`、`pulling`、`pinned`。缺少任一必要镜像即拒绝。

清理候选必须同时具有 `io.lmm.project=api.lmm.best` 和 `io.lmm.managed-by=dp28` 标记。被任何容器引用的镜像保留。输出不包含容器或卷删除项。当前 Dockerfile 没有这些标记，因此不会默认把已有镜像当作可清理资源。不能靠改目录名或给现有资源临时贴标签扩大授权。

本轮没有 Docker，未连接 Engine、未收集真实共享层、未实际移除镜像。正式适配必须在同一项目锁下刷新 Engine 引用，再对精确候选操作并复测剩余空间。不得执行全局 prune，不得直接遍历删除 Docker 的内部层目录、日志文件或卷。

实际服务器还须分别计入下载缓存、镜像内容存储、展开快照、容器可写层及运行日志。共享层只计算一次；它被保留镜像引用时不能当作可释放空间。Engine 与文件系统统计对齐后才可接入 DP-27 的真实产物和 DP-30 的组合验收。
