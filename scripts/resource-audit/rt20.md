## 实际预算与命令

测试进程硬限制：地址空间 2 GiB；CPU 累计 10 秒；固定到一个可用 CPU；文件描述符 64；输出文件 1 MiB；禁止 core dump。外层限时 12 秒，Go 测试限时 11 秒，每个客户端连接限时 3 秒。

负载限制：总计最多 16 个请求、4 个同时打开的客户端连接、16 MiB 请求线上字节、每个正文最多 4 MiB。测试使用默认 4 MiB 大请求阈值，测试池容量为 2。超出预算会失败并清理连接，不重试、不持续施压。编译在负载开始前完成，使用已安装工具和本地标准库，不下载依赖。

注意：2 GiB 是内核强制的地址空间上限，不是 128 MiB RSS 上限。128 MiB RSS 是每 50 毫秒采样的额外停止线；`GOMEMLIMIT=64MiB` 是 Go 的软目标，不能冒充硬限制。当前主机 cgroup 只读，本任务没有修改它或绕过主机策略。

```sh
# 在含本 PR 文件的本地源码目录执行。输出目录必须尚不存在。
python3 scripts/resource-audit/rt20.py --out /tmp/rt20-evidence
```

脚本只复制已校验的原始 limiter 与本次测试文件，再运行：

```sh
GO111MODULE=off GOWORK=off GOTOOLCHAIN=local GOPROXY=off GOSUMDB=off \
  CGO_ENABLED=0 GOMAXPROCS=1 GOMEMLIMIT=64MiB \

# 脚本随后在设置硬限制后执行，不能省略受限启动器：
```

不要设置环境变量后直接运行二进制来绕开启动器。测试会检查硬限制。成功退出仅表示组件探针通过，报告的 `main_acceptance` 仍为 `NOT_RUN`。

## 已执行结果

运行时间：2026-10-10 14:12–14:13 UTC。Go 1.23.2，Linux amd64。
进程运行 2.349687 秒；10 个请求；峰值 3 个客户端连接；实际预留/发送请求字节 8,389,947（包含 HTTP 头）。测试没有触发停止线，没有自动重试。没有残留测试进程。

两条慢正文连接各声明 4 MiB，但只发 1 字节，持有两个名额。测试客户端 B 的 4 次小正文请求全部成功，延迟分别为 0.221、0.105、1.503、0.094 毫秒。B 的大正文请求仅发送头部，在池已满时得到 429，延迟 0.050 毫秒。这证明组件有全局拒绝行为，不证明账号之间有预留名额或公平调度。

关闭两条慢连接后，服务器继续运行，没有通过关停服务器或强制 GC 制造恢复结果。恢复后，4 MiB 正文请求成功，延迟 18.311 毫秒。另一个合法 4 MiB 慢客户端在首字节后暂停 200 毫秒，最终成功，耗时 221.968 毫秒。成功请求均校验完整正文的 SHA-256，不以 HTTP 200 作为唯一依据。

## 定位到的源码入口（尚未证实耗尽漏洞）

- `apps/api-go/main.go` 的 `runServer` 用 `http.Server{Addr, Handler}` 构造主监听器，未显式设置读头、读正文、写入或空闲超时。未验证实际边缘代理策略，不能据此认定生产没有任何限制。
- `apps/api-go/middleware/relay_admission.go`：`RELAY_LARGE_REQUEST_MAX_CONCURRENCY` 默认 0；启用后按进程共享。小正文不占该池，名额在下游 handler 返回时释放。
- `apps/api-go/router/relay-router.go`：解压中间件在认证和大请求准入之前注册；实际 relay 的认证、准入、分发顺序已读取。
- `apps/api-go/middleware/gzip.go`：同时限制线上压缩字节和解压后的读取字节；gzip 初始化会读取头部；zstd 解码并发设为 1。这些代码存在，不等于复杂压缩输入的内存、CPU 和恢复已验收。
- `apps/api-go/service/system_task.go`：存在数据库任务领取、运行和取消路径。容量 1 的 `systemTaskWakeup` 是唤醒通知，不是业务任务队列容量。数据库排队上限、执行并发和依赖失败恢复未测量。

以上读取均固定在报告基线；不将未来 main 的变化算入本轮结果。
