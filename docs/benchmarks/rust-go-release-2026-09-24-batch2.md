# Go / Rust 优化构建对比：第二批

本轮仅比较已跑通的公开读取与非流式 chat 转发。Rust 尚有 95 条当前 Go 路由缺少源码声明、26 条占位，不能将本轮测试解释为完整后端已对齐。

测量前完成全量 Rust 测试 1733 项、193 项真实依赖测试及失败夹具的定向修复复测；新 CI 现场 Go 对照和回归合计 68 项通过。格式检查、全 workspace Clippy `-D warnings` 与优化构建通过。

配置：同一台 24 逻辑 CPU Linux 主机；Go/Rust 各 4 个运行线程、10 个数据库连接、30 分钟连接寿命。使用同一隔离 PostgreSQL 18.6、不同 Valkey cache DB；运行期间没有本任务的编译或其他测试。每端一个输出日志文件，均保留逐请求访问日志。Go 关闭额外镜像日志文件；Go 文本和 Rust JSON 日志格式保持原样。

结果取每组 3 轮的中位数；延迟列是 3 个批次各自 p95 的中位数，非合并后的分布。CPU 是后端进程的平均 CPU 毫秒/请求。RSS 每 10 ms 采样，原始文件另存进程生命周期峰值、PSS、私有内存和 swap。

## 带真实资金结算的转发

使用普通 `/v1/chat/completions` listener 和本地确定性 provider，每端一组独立账户/API key，模型倍率与完成倍率均为 1。每个响应为 512 prompt + 128 completion tokens，精确扣除 640 quota。三个并发级别、每级三轮、每轮每端 500 次，共 9000 次测量请求；含首次请求与预热，共 9602 次 provider 调用，拒绝数为 0。

| 并发 | Go req/s 中位数（范围） | Rust req/s 中位数（范围） | Go p95 ms | Rust p95 ms | Go CPU ms/请求 | Rust CPU ms/请求 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 17.47（15.18–19.51） | 41.49（34.81–42.32） | 39.97 | 23.32 | 7.887 | 3.253 |
| 8 | 26.63（23.18–37.01） | 42.22（35.47–44.11） | 1435.98 | 657.69 | 8.080 | 3.660 |
| 32 | 27.08（25.82–48.54） | 42.54（39.07–43.42） | 2177.80 | 1485.90 | 8.713 | 3.753 |

本轮 Rust 的转发吞吐中位数较高，Go 的三轮波动较大，部分单轮 Go 高于 Rust。并发争用同一账户余额行，且涉及持久化提交；此结果不代表多账户吞吐、外部模型时延、流式响应或语言本身的速度。

每一批均验证钱包、token 两个余额计数、用户次数、渠道累计额度、日志条数/额度/prompt/completion 和未完成结算。最终每个账户：4801 次请求、3072640 quota 消耗、4801 条日志、pending=0，钱包和 token 余额均为 996927360。最后一次共享渠道观测为 6145280，恰好等于 9602×640。原始 `accounting` 是各后端最后一批之后的观测：Rust 的共享渠道数在最后一批 Go 请求之前读取，因此与 Go 的末尾观测时间不同；各批都按当时总请求数核验。

原始数据包含 HTTP 结束后等待账本可见的时间与相应吞吐；这段时间也包含本地 psql 验证开销，不应解释为纯异步结算耗时。
