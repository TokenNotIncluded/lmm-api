# Rust 核心与 Go 扩展迁移（WIP）

分支：`wip/rust-core-go-extensions`，PR #675。
这是替换旧 Rust 后端的新迁移，不是继续复制整个 Go 后端。
**保持 Draft；不合并、不上线、不改生产密钥、用户余额或数据库。**

## 已落地的范围

P0 已删除旧 Rust 源码、旧独立迁移器、发行版打包、旧部署入口和测试流程。
Go 回归需要的三个 JSON 样例移到 `contracts/go-regression`。
保留现有 Go/Web 服务、发布安全校验和独立 `apps/lmm` CLI。
历史 Rust 部署事务必须由其已验证的旧操作程序人工恢复，不能用新核心接管。

本次继续实现 P1 的原生身份部分，不再只有数据类型和健康检查：

- PostgreSQL 独立 `core_identity` 表：用户、会话、API Key、团队、成员、邀请、授权版本与审计。
- Rust 独立验证凭证、停用状态、有效期、用户版本和团队消费权，不调用 Go。
- 会话与 API Key 分开；模型 Key 不能创建团队、邀请成员或签发更多 Key。
- 创建团队、分页列出团队、邀请/接受邀请、移除成员、签发/撤销 Key 已有真实 HTTP 接口。
- 随机凭证只返回一次，数据库只保存摘要；身份接口禁止缓存，不把凭证写进审计。
- 写操作与审计在同一事务内；成员版本阻止退出后重新加入恢复旧 Key 或旧邀请。
- 明确的迁移命令和离线测试用户初始化命令；服务启动不自动改表。
- 可选 Docker 身份栈包含独立 PostgreSQL 数据卷、内部网络、文件密钥和单独运行的管理命令。

`apps/extensions-go` 仍是独立模块宿主，注册列表为空，没有数据库句柄或模型转发入口。
`contracts/core/v1` 保留 Go/Rust 共用的 24 组付款边界样例。

**身份验证可以运行，不等于完整 API 后端已经完成。**
`/health/live` 返回 200；即使身份验证成功，`/health/ready` 与模型接口仍返回 503。
没有允许提前接管流量的开关。尚未接通旧 Go 用户/Key 导入、正式登录/OAuth、完整账本、
预算、订阅抵扣、路由转发和协议转换。现有 Go 继续处理生产请求。

## 服务权属

| 范围 | 最终唯一负责方 | 边界 |
| --- | --- | --- |
| 用户、登录、会话、Key、OAuth 授权与撤销 | Rust 核心 | Go 扩展不能直接修改核心表。 |
| 个人/团队账号、成员关系、消费授权、预算 | Rust 核心 | 操作人、资源归属、实际付款账号分开。 |
| 价格、预留、结算、退款、订阅抵扣 | Rust 核心 | 同一事务检查权限、额度和预算，整数记账。 |
| 渠道、路由、转发、协议转换和流式输出 | Rust 核心 | 关键路径不依赖 Go 可用性。 |
| 商店、工具市场、活动、通知、推荐与辅助控制台 | Go 扩展 | 使用有版本且受权限限制的核心接口。 |
| 支付平台、邮件等易变适配 | Go 扩展 | 核心验证原始凭据、订单和去重记录，不信任任意金额通知。 |

初期只拆一个核心进程与一个扩展宿主，不拆大量小服务。
Go 模块显式注册，不把 Go 动态库或任意脚本放进 Rust 进程。
管理角色和消费权限是独立授权，模块服务凭证也不能替代用户授权。

## 团队是原生账号

独立团队 WIP #656 已关闭，未合并。保留其 [设计](team-accounts.md) 与安全测试场景，
不照搬依赖 Go 会话、控制器和数据库迁移的实现，也不恢复第二套团队身份写入方。

个人始终是登录人；团队没有共享密码。每人可创建一个团队、加入多个团队。
账号由 `kind + id` 标识。平台 L0–L6、团队成长等级与团队角色不能混用。
L5/L6 不自动获得团队资金使用权，L0 成员加入团队也不改变个人等级。
本批保存平台等级，团队成长等级、账号状态继承政策仍需独立实现。

团队创建者只记录在团队表，成员表不重复保存 owner。
owner 可以管理 admin/member，admin 可以管理 member；普通成员只能退出自己。
`can_spend` 独立于管理角色。接受邀请时重新验证接收人、原邀请会话、邀请人当前权限、
团队版本与双方成员版本。邀请邮件可由 Go 发送，但邀请有效性始终由 Rust 决定。
成员移除后保留版本记录，不能靠退出/重进清除将来的账务和预算记录。

个人 Key 默认只使用个人余额；明确配置后才能使用已获消费授权的团队。
团队 Key 只能使用所属团队，不能回退到个人或其他团队。
逐 Key 的账号顺序与各账号内部的订阅/余额顺序分开。
撤销、停用、权限错误、数据库错误和未知结果必须停止，不能当作余额不足继续换付款人。

身份接口输出的是当前授权快照，**不是扣费预留许可**。
后续计费必须在自己的事务中重新校验权限并预留，固定付款人、价格版本、预算周期和
订阅/钱包分项。流式输出、重试、结算、退款不能重新选择付款人。
保留每美元 500,000 credit 的现有单位，检查溢出，不用浮点数结算。
当前额度类型不代表账本已经实现；负债必须有独立类型与审计规则。

## 核心不能依赖扩展在线

目标模型路径：Key/账号验证 → 价格和预算检查 → 原子预留 → 固定付款与路由信息
→ 上游转发与协议转换 → 计量和结算。没有同步向 Go 查询身份或扣费的步骤。

配置由核心校验并持久化，扩展失效时使用最后有效配置。
通知等事件应和业务事务一起写入待发记录，再限量投递、去重和重放。
队列必须有上限；事件不是账本，重复事件不能重复扣费。
只读身份查询使用一致的数据快照，不锁团队记录；团队写操作使用明确的锁与版本检查。
这不是吞吐量承诺，性能仍需基于真实路由和计费负载测试。

容器没重启不等于真实模型 token 输出不中断。

## 发布与连续输出

普通功能更新只构建并部署 Go 扩展，不重启无变更的核心或数据库，不自动迁移核心表。
核心自身升级需要至少两个就绪实例：新实例接新请求，旧实例保留已有连接和结算，
等待结束后退出。不能为部署方便给所有流设置短总超时。
单实例、主机故障或关闭等待超时仍可能断流，不能承诺任何故障下绝不掉流。

核心和扩展镜像应分别编号、锁定摘要并验证来源。
数据库变更先增加兼容结构，再验证新旧代码，最后移除旧结构。
账务回退不能恢复旧快照而丢弃新交易。
当前只有隔离开发栈，未发布生产镜像、迁移生产数据或改动线上反向代理。

操作方法见 [原生身份开发指南](core-identity.md) 和 [Docker 指南](../deployment/docker/README.md)。
