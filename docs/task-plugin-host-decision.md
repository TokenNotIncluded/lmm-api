# ADR: reject the current upstream task-plugin host migration

Status: **current architecture rejected; future proposals require a new decision**. Reviewed 2026-10-03 against LMM `f59bdbdd8f17f8f714bcc6c1fe6824ec57e18d3e` and the full discussion in [issue #405](https://github.com/TokenNotIncluded/api.lmm.best/issues/405).

## Decision

Keep the native Go relay/task adaptors and declarative Advanced Custom routes. Do not import the upstream JavaScript task runtime, plugin override store/admin UI, type-60 plugin bindings, or image-provider migration. Do not add placeholder compatibility fields or advertise unsupported plugin protocols. Type-60 channels retain their existing compatible-relay behavior. Pricing, group ratios, model price locks, `/fast`, OAuth restrictions, and administrator assistant behavior retain their existing owners.

This resolves #405's architecture investigation through its explicit rejection option. It does not claim provider parity, enable Seedance 2.5 draft/final workflows, or permanently exclude a smaller provider-neutral contract.

## Why reject this migration now

[Upstream multi-plugin bindings](https://github.com/QuantumNous/new-api/commit/4c34f25a49f1cf491479e3842b2251e8a6908851) change channel validation, binding permissions, routing and persisted task execution context. They require explicit upstream kinds and plugin capabilities, and bound the extension list to 32. LMM has none of that host contract; ordinary channel editing and an existing enum value cannot safely substitute for it.

[Upstream OpenAI Images migration](https://github.com/QuantumNous/new-api/commit/03563a4a791629a811076f1cbcbecfbe2716eac2) adds 4,027 lines and removes 1,404. It replaces Ali's native image path, introduces synchronous polling over durable tasks, detached submission on client disconnect, multipart references, result-retention semantics, and image-count settlement. Those are changes to who owns accepted provider work and money, not just another response converter. No native-versus-host/provider parity evidence has been established for LMM. Retaining the tested native path is the supported choice until such a migration is demonstrated.

The missing reusable behaviors are real, particularly multi-protocol task extensions on compatible gateways, inline task delivery/retention, draft dependencies and schema-driven pricing. They do not by themselves require an executable script host. A named provider workflow should first establish which gap cannot be served by Advanced Custom or a small native adaptor change; then compare that change with a separately specified host contract.

## Conditions for a future proposal

1. **Concrete provider evidence:** identify vendor, model, route, request/response fixtures and a reproducible unsupported workflow. The migration candidates raised upstream are Alibaba/Bailian image generation/editing and Doubao image/video protocols; their actual vendor behavior must be compared with the native path, starting with one provider. A claimed gateway benefit also needs a real type-60 gateway configured for that provider protocol. Keep Ali/Doubao native paths until equivalent tests pass; do not enable new model IDs from upstream metadata alone.
2. **Host-owned boundaries:** define API version/capability negotiation, an explicit bounded plugin list, route/channel/upstream claims, separate bind/manage permissions, and pinned plugin execution identity for in-flight tasks. Unknown or unavailable claims fail before upstream work; channels without bindings remain unchanged. Plugins supply validated facts, not quota writes or replacement settlement logic.
3. **Financial and delivery parity:** test generation/edit conversion, multipart references, cancellation/timeouts before and after provider acceptance, multi-image/Base64 output, payload-less results, and reported usage. Validate image counts against an explicit bound (the current request bound is `MaxImageN=128`), preserve upstream `metadata.usage`, and prove wallet/subscription/token settlement, price locks, group routing, `/fast`, OAuth and assistant policies still run through their existing owners. Persisted-task failure/restart and competing terminal CAS tests must establish the new submission boundary explicitly. [Upstream #7507](https://github.com/QuantumNous/new-api/pull/7507) restored metadata that its image migration had dropped.
4. **Origin-task parity:** resolve a bounded, deduplicated list of public task dependencies under the authenticated user; reject missing, foreign or provider-incompatible tasks before sending upstream. Preserve origin channel affinity, then translate to provider IDs. Cover JSON, multipart and every retained request surface. [Upstream #7547](https://github.com/QuantumNous/new-api/pull/7547) only adds decoder intent because its host already owns those checks. A native Seedance draft/final proposal needs the same contract even if no plugin host is adopted; this ADR leaves that workflow unsupported.
5. **Non-destructive capability evolution:** opening or previewing saved pricing must preserve the expression. Narrowed enum branches may become unreachable; unknown fields/types still fail closed. Explicit editing regenerates reachable tiers without zeroing their prices. Cover 1080p/4k → 480p/720p narrowing. [Upstream schema fix](https://github.com/QuantumNous/new-api/commit/9a0be8750a6d736d9692535ed2cd68f8eec46529) demonstrates the failure mode; LMM's current numeric editor is not that task matrix.
6. **Bounded runtime and rollout:** specify execution/admission/network/payload budgets, source/icon/upload limits, database-portable storage, hash-only cluster snapshots, and retention of the last working plugin when loading/compiling a change fails. Upstream needed both [long-text storage and an 8 MiB cap](https://github.com/QuantumNous/new-api/commit/c0cff23a3af8e68809647bd39ec204bedbea28af) and [hash-first synchronization](https://github.com/QuantumNous/new-api/commit/2c175190c44a95c6af4877e901dc5211ef706979); copying its size limit alone would not establish LMM's resource budget.
7. **Admin and observability parity:** blocked disable/delete must expose one clear destructive confirm and one cancel, with explicit cascade/force semantics and the normal mutation lifecycle; cover channel/in-flight usage blockers as in [#7528](https://github.com/QuantumNous/new-api/pull/7528). Inline terminal success/failure must have an explicit sync marker and initialized, high-resolution timing, while legacy `use_time` remains readable and async submit logs retain their meaning. [#7553](https://github.com/QuantumNous/new-api/pull/7553) now uses millisecond `other.ut` at head `2a493eb8626aa8705956e45808538ad7f8e1caae`; its earlier uninitialized-start fixture is no longer the current patch. Timing metadata must remain observational.

The follow-up fixes above are evidence for future acceptance, not standalone LMM backports. This decision adds documentation only; it installs no runtime, performs no provider migration, and claims no new provider acceptance tests.
