## 1. 两层顺序，不复制计费系统

第一层是每个 API Key 保存的**付款账号顺序**。第二层是付款账号内部的
**订阅／钱包顺序**。不要把所有账号的余额和套餐合并成一个资金池。

- 个人 Key 默认只使用自己的个人账号。加入新团队不会自动增加付款来源。
- 个人 Key 可以明确选择已获消费授权的多个团队，任意排序，也可以去掉个人账号。
- 团队 Key 只能使用所属团队。不能使用创建者个人账号，不能追加其他团队。
- 团队自己的订阅仍可用：此处“只能使用团队余额”规定的是资金归属边界，
  不禁止用户同时要求的团队套餐。需要严格仅余额时，团队可选择 `wallet_only`。
- 所有未列出的账号都不可使用；列表末尾不会自动追加个人钱包。
- 登录账号切换只改变控制台视图，不改变已有 Key 的归属或付款顺序。

账号内部继续使用现有 `billing_preference`：

| 值 | 含义 |
| --- | --- |
| `subscription_first` | 先用订阅，再按套餐规则使用同账号钱包 |
| `wallet_first` | 先用钱包，不足时尝试同账号订阅 |
| `subscription_only` | 只用该账号订阅 |
| `wallet_only` | 只用该账号钱包 |

具体订阅选择、模型适用范围、重置周期和 `AllowWalletOverflow` 继续由现有
套餐逻辑决定。不能仅把这四个值展开为两个随意尝试的函数，绕过套餐限制。

个人 Key 可单独选择自己的订阅／钱包偏好，或明确继承个人设置。新创建的
版本 1 个人 Key 默认 `wallet_only`。旧 Key 保留原有个人订阅偏好，不因迁移
突然停用已购套餐；两者均不会自动使用团队资金。

团队的内部偏好由创始人设置，或由其明确授权的管理员修改。个人 Key 引用团队时
只能继承该团队的设置，不能覆盖它。团队 Key 也继承所属团队的设置。

例：个人 Key 的账号顺序为 `团队 A → 个人 → 团队 B`；A 选择订阅优先，个人
选择仅余额，B 选择余额优先。结果是先尝试 A 的付款规则，再尝试个人钱包，
最后尝试 B 的付款规则。这个例子不表示允许把一笔请求拆给三个账号共同付款。

### 拟定的持久化结构（尚未接入接口）

```json
{
  "version": 1,
  "account_order": [
    { "kind": "team", "id": 42 },
    { "kind": "personal", "id": 7 },
    { "kind": "team", "id": 91 }
  ],
  "personal_billing_preference": "wallet_only"
}
```

`id` 是稳定的账号标识，不是 handle。Key 所属账号由数据库读取，不接受客户端
任意指定。团队消费授权是服务器数据，不属于上述请求结构。

首次解析时，缺失或 `null` 的顺序表示仅所属账号；显式空列表为配置错误。
更新接口必须区分“没有提交这个字段”和“明确恢复默认”：前者保留已有值，
不能误把部分更新当作恢复默认。无效版本、重复账号、其他个人账号、无消费授权的
团队都拒绝整份配置，不静默删除其中一项再继续花钱。

操作人、Key 所属账号、实际付款账号；现有“token.user_id 必须等于扣款 user_id”
这类条件必须按新的授权关系重构，而不是删除条件或伪造一个团队用户。

它没有被任何生产入口调用，不能代替真实事务内的权限校验。

## 3. 选择、预留、结算

请求发出前：校验 Key、固定保存的策略版本、校验全部列出账号的授权，再按顺序
尝试付款。每个候选账号按自身合法的模型分组、价格和套餐报价；Key 自身的模型、
IP、调用范围限制同时适用。不能先用个人优惠计算，再让团队按该优惠付款。

只有明确的“余额不足／没有适用套餐／周期额度不足”才属于可尝试后续已配置账号的
结果。团队／成员预算用完也可转到已明确授权的另一个账号，但不能继续扣原团队。
Key 的跨账号总额度用完必须拒绝，不能靠换来源重置。模型权限拒绝、账号停用、
退出团队、授权撤销、数据库故障或未知错误都停止请求，不以切换付款账号掩盖错误。

单次请求采用**一个付款账号**。同账号订阅加钱包的现有组合仍可使用，但必须遵守
套餐是否允许溢出及异步任务限制。不同个人／团队之间不做拼单扣款。

“优先”按能否覆盖本次完整预留判断，不是先把第一个账号扣到零再换下一个账号。
候选预留失败后，必须确认全部相关预留已撤销，才可尝试下一个账号。
不确定是否成功的扣款只能查原记录，不能对下一个账号再次扣钱。

请求一旦开始，付款账号、价格依据、订阅／钱包分项和预算周期被固定。
上游重试、流式输出、WebSocket 后续结算、异步回调、退款，都不得重新读取排序
选择新的付款人。新增消费窗口仍检查权限和预算；不再允许的新窗口停止。
成员退出或 Key 删除后，已发生费用仍记到原账号，退款也仍返还原账号。

每个逻辑请求保留唯一记录，覆盖预留、补充预留、结算、取消和对账状态。
重复回调、进程重启、超时不能重复扣款或退款。不得把余额为零、错误或未知状态
当作免费调用，也不能声称上游不可控制的最终费用绝不会超出估算。

## 4. 成员、角色与授权

每位用户可创建并持有一个团队，也可加入多个团队。团队没有共享登录密码。
始终使用个人身份登录；团队只是所操作的账号。

保留创始人、管理员、成员三个角色。创始人唯一，可管理全部成员；管理员可管理
普通成员和自己的受限设置，不能管理其他管理员或创始人；成员只能管理自己。
默认管理员管理全部普通成员，暂不增加管理员各自的小组。不得复用全站管理员角色。

邀请支持站内 ID／邮箱以及站外邮箱／链接；接受前显示角色和预算。创始人可邀请
管理员或成员，管理员只能邀请成员。接受时重新检查邀请人的当前权限；链接具有
到期、撤销和使用次数限制。管理员邀请绑定已验证邮箱。加入不等于无限消费授权。

个人 Key 使用团队资金，需要有效成员关系和团队消费授权。只有个人 Key 的持有人
能决定是否加入自己的付款顺序；团队管理员不能偷偷修改其个人 Key。
Key 已交给客户端时，扩大可用资金来源需要明确确认；OAuth 应用仍受原同意范围限制，
不能因为加入团队或修改设置而自动扩大客户端付款权限。

团队 Key 记录负责人和创建人。负责人离开时停止新请求，由有权人员重新分配并
轮换 Key 后才能恢复；首版不提供可绕过成员预算的无负责人服务 Key。

## 5. 分层预算、转账、套餐

创始人可设置团队总预算和所有人的上限；管理员可在创始人上限内限制自己与成员；
成员可在上级上限内调整自己的限制。规则分别保存，不能通过改写一行覆盖上级限制。
日／周／月及自定义重复或指定范围可同时存在，按统一团队时区计算。

所有适用上限同时成立；不同周期不能简单换算后取一个数。已用、执行中预留和本次
预留一起检查，并与扣款同一事务提交。更改周期、时区、角色、Key、handle 或退出重入
都不能清零本周期消费。`0` 是禁止消费，未设上限不是 `0`。

成员对同一团队的消费合并计算，无论来自团队 Key 还是其个人 Key。套餐抵扣也计入
该成员的团队使用预算。其个人付费不能消耗团队预算；Key 本身的总限额则跨付款来源。
团队预算不是把余额预先转给成员，也不意味着个人 API 使用上限可以授权转账。

个人↔个人、个人↔团队、团队↔团队均支持转账。团队向外转账、套餐购买和自动续费
需要独立资金操作权限及限额；默认只有创始人，管理员需明确授权。普通成员不能把
团队资金转到个人钱包再绕过使用限制。团队操作不得重复触发个人注册／首充奖励。

团队套餐归团队，额度和限购按团队计算，不按人数复制。套餐支付和使用分别记账。
团队付款失败不会自动扣某个成员个人钱包；个人给团队补钱需要明确操作。

## 6. handle、卡片与界面

个人和团队共享 `@handle` 名称空间，数据库唯一约束保证先成功保存者获得。
handle 独立于登录名，规则为 3–30 个 ASCII 小写字母，保留词统一维护。
个人和团队分别每自然月一次修改机会，按固定平台时区计算；团队仅创始人可改。
旧 handle 保护 30 天后释放，历史交易仍绑定账号 ID，不绑定旧名称。

`/@handle` 默认只公开主动选择的资料；余额、邮箱、成员名单、明细和对话内容默认
不公开。原有 SVG 分享开关及撤销保持有效。银行卡比例的身份卡展示头像和 handle，
不展示虚构卡号或支付标志。个人与团队徽章复用同一编辑器，视觉延续首页的留白、
粒子和几何形态；亮／暗主题分别校验，动画不持续占用列表资源。

头像菜单提供当前账号、切换账号、身份卡、API Key、我的团队、创建／加入团队。
团队管理栏目仅创始人／管理员可见，内部按权限区分。成员主要看到自身预算、
重置时间和 Key。全站管理入口与团队管理彻底分开。

Key 编辑页展示可排序的付款账号列表，每行明确显示个人／团队及其内部付款偏好。
未勾选的账号不参与；团队 Key 的账号选择锁定，团队内部偏好显示为继承值。
保存前显示完整顺序与最后来源，不能只显示含糊的“自动选择”。

账号切换不覆盖登录身份。请求、缓存、分页、导出和订单按账号隔离；每个标签页
独立保持当前账号。切换后旧异步响应不得写入新账号页面；已创建订单不改变归属。

## 8. 本批验证范围

独立规则包只依赖 Go 标准库，可以不下载项目依赖运行：

```sh
cd apps/lmm-extensions
GO111MODULE=off go test -race -cover ./pkg/accountfunding -count=1
GO111MODULE=off go vet ./pkg/accountfunding
GO111MODULE=off go test ./pkg/accountfunding -run '^$' -fuzz=FuzzResolveOrder -fuzztime=10s -parallel=2
```

这只验证纯规则，不代表数据库权限、预算并发或真实扣费已经通过测试。
模块环境可去掉 `GO111MODULE=off`；现有 `Billing safety regressions` 工作流仅保留
手动 `workflow_dispatch` 入口，可运行该包的 race 测试和原有服务计费回归。
日常验收使用本机测试。完整仓库基线检查和端到端验证必须在
可用的完整工作区继续执行，不以本批 100% 语句覆盖率代替整体完成度。
