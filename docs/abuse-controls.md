# 注册滥用、蜜罐与封禁通知

[文档目录](README.md) · [架构](core-migration.md) · [业务验收](microkernel-business-acceptance.md)

本文记录已确认的产品行为和接线要求。2026-10-15：蜜罐领域、模型、身份、管理页与
Python 管理工具正在私有候选中组装和验收，尚未接入本分支运行链路或部署。普通
封禁的邀请者警告邮件仍缺注册邀请关系、封禁接口和投递队列接线。不要把候选、
模板自测或已有线上单体功能写成新架构已完成。

## 事件与相似账号

先保存发现时间、实际注册时间范围、明确账号清单、操作前后状态与服务端证据。
保留账号、原始失败和未知结果；不删除记录。原始用户名、邮箱、IP、日志与凭证
不进入公开 Git，私有证据只存既有备份根。请求日志没有账号映射时，不推断某 IP
属于某账号；同一请求跨节点重复出现时，不累加为多次注册。

重复邮箱、邮箱本地段模板、相同来源 IP、注册聚集、用户名模板和邀请关系可形成
复核候选。共用域名、名称缺少语义或同一邀请者均不能单独证明滥用。客服 AI 可读
服务端生成的相似度特征并建议复核；最终标记、权限和资金操作仍由 Core 授权。

## 静默蜜罐

管理员显式标记账号并选择策略。账号保持登录和个人 API Key 管理外观，不向用户
返回蜜罐字段、专用封禁提示或内部原因。普通 disabled 与蜜罐是不同状态；将已
禁用账号转为蜜罐必须单独预览和确认，不能在普通标记时偷偷解封。

| 模式 | 行为 |
| --- | --- |
| 固定文本 | 管理员设置回复内容，按客户端协议返回完整 JSON 或流式终止 |
| 自定义上游 | 每种客户端协议分别设置上游及其协议，复用现有协议转换 |

本批客户端范围是当前公开的 Chat Completions、Responses；上游转换覆盖已有
Chat、Responses、Anthropic、Gemini。其他客户端入口不在这一批范围。当前候选
自定义上游只接受数字回环地址；外部 HTTPS、DNS/IP 约束与真实供应商仍待接入验收。

蜜罐传输独立于正常渠道、真实开发者授权和计费链路，不调用正常供应商，不预占或
扣除用户真实额度，也不伪造付款、到账或历史账本。凭证由宿主独立加载，管理界面
只选择别名；不得转发用户原 Authorization、Cookie 或正常渠道密钥。模型列表来自
管理员明确的公开名称与 Key 限制，不枚举私有组。

策略独立限制每用户和全局请求频率、并发、输入输出大小、输出数量、输出速率和
总超时。计数与租约由数据库维护，重复请求、断连、取消和进程退出也必须受约束。
超限使用普通模型限流响应。固定内容可能被识别；不承诺行为完全不可察觉。

标记不得授予团队资金、Commerce、MCP 或 Remote 能力。所有新资源入口需要逐项
拒绝矩阵。标记之前已预占的真实操作仍按原规则结算，不清除或伪装历史 hold。

## 管理操作

Web 和 Python 管理工具调用同一 Core API，不直接修改数据库。管理权限要求真实
超级管理员会话，不能用服务等级或普通 API Key 替代。批量操作绑定明确 ID、策略、
原因、当前 revision 与 operation_id，先展示预览，确认后原子提交。未知结果查询
原操作，不自动生成新操作重试。解除蜜罐不提升等级、不恢复已撤销 Key、不改余额。

Python 工具是低频薄客户端，不是额外常驻服务。原始身份导出使用私有文件，默认
终端输出不包含邮箱、IP 或凭证；参数错误也不能回显误放在命令行里的秘密。

## 注册、登录与访问限频

同一 IP 的注册限制、登录限制和普通访问限制使用不同配置、计数 scope 和设置页。
蜜罐模型限速不能代替它们。反代部署必须先明确可信代理与真实客户端 IP 解析，
不能将所有用户计入回环地址，也不能信任任意客户端伪造的转发头。注册昂贵计算、
发信和奖励之前执行限制，多实例共用原子计数；重启不能简单清空限制。

这部分设置页及完整接线仍待实现，现有固定 auth 限频不代表已满足上述需求。

## 邀请者警告邮件

普通封禁时，仅有真实注册邀请者的账号显示“给邀请者发送警告邮件”，默认不勾选。
它与额外扣罚是两个独立选项；邀请关系不代表邀请者参与违规。静默蜜罐不默认通知。
收件人必须由 Core 保存的注册关系确定，不能使用团队邀请代替，也不能由客户端
提交任意收件人。没有可用邮箱时明确显示不能发送。

预览展示收件人、被封账号 ID、用户名、邮箱、公开封禁原因、上诉入口和用户协议。
内部风控证据不自动外发。正文转义用户输入，链接来自管理员控制的正式站点配置。
批量预览同时核对每个收件人与被封账号，内容或关系改变后重新确认。

封禁真相和通知意图由 Core 事务记录，Go 扩展负责自己的发信 outbox 与投递，不直读
Core 数据库。发信失败不回滚封禁；待发送、已提交、失败与结果未知分别记录。
队列幂等不等于 SMTP 只投递一次，缺失确认不能盲目重发。当前仅模板和预览候选，
真实发信与邮箱验证、邀请关系迁移、设置页、管理动作仍待独立验收。

## 验收边界

验证真实数据库下的管理权限、原子批量修改、冲突、重放、跨实例限速与租约；
模型 HTTP/SSE 验证每种转换、断连、超时及零真实资金变动。正常账号作为对照，
旧在途操作保持真实结算。安装校验、新组件指纹和受限运行权限同时验证，普通
启动不执行 DDL 或升级已有库。最后分别完成 Web、Python 与真实邮件投递验收，
保留失败和未运行项。开发自测不能代替独立签收，部署与源码提交分开记录。
