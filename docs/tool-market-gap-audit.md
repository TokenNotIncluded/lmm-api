# LMM 工具市场：需求与仓库实现差距

核查日期：2026-09-19。基线：`4524697e8` 及核查时的本地工作树。

后续实施进度见 [工具市场实施记录](tool-market-implementation.md)。下文保留开始实现前的差距基线，不能当作实施后的最新功能清单。

结论：仓库已有账户、模型渠道市场、两个内置 MCP、原子余额预扣、财务流水、开源悬赏和基础 WebMCP；尚未找到需求书定义的通用 MCP 工具市场闭环。建设重点是新增市场业务模型、用户工具集、授权策略和调用交易流程，再接 Remote 与 Serverless 两种执行后端。

本次检查了 Go 主后端的路由、模型、服务、MCP 控制器，Web 页面与 WebMCP，以及 Rust MCP 入口。README 将 Go 标为默认生产后端，Rust 标为预览后端。本报告不代表线上已部署状态，也不是完整安全审计。未修改业务代码，未读取生产数据库或凭证。工作树原有其他改动未纳入本次修改。

## 本次对话确定的范围调整

用户明确取消提现机制，并要求“直接划转，留划转记录”。据此：

- 成功调用按确认价格和费率直接划转至作者账户和指定平台收款账户。
- 不建设待结算收益池、提现申请、外部收款账户、提现审核或打款流程。
- 保留调用记录与划转记录的关联、划出方和划入方、金额、费率快照、时间及防重复处理标识。
- 退款关联原交易，追加退回或冲正记录，不改写原划转事实。
- 用户调用前的金额冻结、执行结果待确认仍有必要；它们不属于作者收益提现或延迟结算。
- 原第 20 章应改为“作者收益与划转记录”；第 2、19、21、28、29 章中的提现和作者延迟结算条款相应删除或调整。Serverless 作者资源费用仍单独记录。

作者已经花掉收入后发生获批退款的资金承担规则，原需求中的待追回处理仍需明确；取消提现并不会自动消除这个情况。

## 最需要避免的六处直接套用

### 1. 把现有 `/mcp` 改名就称为元 MCP

当前 handler 共享一个固定注册的悬赏 server，并不是按账户和客户端加载工具清单。需要真正加入工具集、访问检查、稳定 Tool ID 和动态清单。现有悬赏客户端已经使用此路径，后续接入市场时还需明确兼容方式，不能无意改变旧入口的工具和授权语义。

### 2. 把站点 OAuth scope 当作 Tool 消费授权

当前注册的是 Pi 与 DSH，scope 对应模型和内置 MCP；授权模型没有 Tool 价格上限、次数和累计预算。现有登录绑定也不是外部资源凭证。应复用 OAuth 核心验证，再补市场授权策略和独立第三方连接记录。

### 3. 只在调用结束后分别改三次余额

用户扣费、作者入账、平台入账、划转记录和调用结算标记必须作为同一笔交易处理，或具备可恢复且不会重复执行的等价机制。否则中途退出会产生少记、重复入账或查不到对应调用的问题。

已有钱包原子预扣可以复用，财务流水有幂等键和冲正模式；但普通钱包退款路径明确是非幂等增加余额，`BillingSession` 的部分完成标记只在内存中。不能仅靠内存锁实现跨实例/重启后的防重。订阅持久化结算与媒体任务退款提供参考，而非零基础重做所有账务。

特别复查：`shouldTrust` 对当前钱包和订阅均返回 false，不能因旧注释提到“信任旁路”就误报当前钱包会跳过预扣。

### 4. 让工具调用直接继承模型任务的超时处理

现有媒体任务超时清理会写 `FAILURE` 并进入退款处理。对可能已在远端发送消息、写入或支付的 MCP，这不足以证明执行失败。需要区分“未执行”“明确失败”“结果未知”，未知状态不能自动重放副作用操作；到期限释放用户冻结金额，也不能把外部操作标成已撤销。

### 5. 复用可关闭的抓取防护作为公开 Remote 接入的唯一边界

已有 SSRF 防护可复用，但其行为受全局开关和允许内网等配置影响。公开作者接入需要专门、明确的出站策略，覆盖服务地址、OAuth 发现、重定向、资源访问和实际拨号。不能把管理员可配置上游地址的信任模型原样交给普通作者。

### 6. 把 Serverless 当成上传入口加一个执行命令

仓库没有可供市场直接复用的 WASM 运行闭环。文件兼容性、宿主能力、调用隔离、资源上限、作者资源计费、取消清理和全局暂停都需建设。可以在同一套市场模型预留 Serverless 类型，但在运行边界完成前不开放用户代码执行。

## 建议的改造顺序

1. **市场对象与权限**：服务、Tool、已审核版本、可见范围、收藏、客户端工具集、授权策略。先把这些边界固定，避免把服务和 Tool 混成一张配置表。
2. **调用与直接划转**：持久化调用记录、价格/费率快照、免费额度和预算预留、冻结、成功划转、失败释放、未知结果处理、幂等和退款。复用现有账户余额，不建设提现系统。
3. **Remote 完整路径**：作者草稿 → 检查/同步 → 审核发布 → 用户授权加载 → 元 MCP 调用 → 划转/退款 → 查询记录。旧内置 MCP 保留兼容。
4. **Serverless 完整路径**：沿用同一目录、授权和调用账务，补运行时、能力约束、资源费用和限额。失败调用的资源成本不能转成用户工具费。
5. **市场运营完善**：统计、评价举报、推广、通知和悬赏成果接入。基础审计、隐私保护和紧急停用必须随前面的功能同时落地，不能留到最后。

这是依赖顺序，不是擅自删除需求书中的 Serverless 或运营功能。当前最适合先形成可验收闭环的是 Remote MCP；Serverless 可以在共享对象和接口确定后单独建设。
