# Original-channel refund execution

This candidate builds on the signed refund core `82e919bd0af6e38a62b91e1e056a1f65c42cd174` and proof adapter `bf330c0c76a19d5b335730c54454a8f2917d4bf6`. It adds one table, `merchant_store_refund_provider_attempts`, to the core's three refund tables. This isolated tree has 20 store tables; the central separately owned coupon table makes the combined capability-4 inventory 21. Neither migration nor worker startup activates capability 4 or changes the writer floor. The central activation command must validate the complete combined schema before enabling refunds.

The original order, gateway snapshot, receipt, verified native payment basis and approved native refund amount remain immutable. Points are the wallet authority, with 500,000 points per USD. Execution never uses the current exchange rate, gateway configuration or another payout destination.

Each approved refund has one durable attempt, keyed by refund ID. Under product → order → refund locks, the broker records an immutable request hash and a 90-second query lease. A `ready` attempt may safely retry only authentication and authoritative lookup. Immediately before the first money-moving POST, a second transaction commits `submit_count=1` and `state=unknown`. Only that successful claimant may send. This count cannot be reset. A crash after that commit, an HTTP timeout, a missing lookup result or a ticket acceptance never permits another POST. Subsequent workers query the same refund business reference. Provider bodies, credentials and customer JWTs are never persisted or logged.

Verified native success/failure evidence is saved in the attempt before calling the core's private completion/rejection primitive. Native success with insufficient merchant platform funds stays `reconciliation_required`: the next worker retries local settlement with the saved proof, without another provider query or refund request. An ordinary ticket rejection is not terminal PSP failure evidence and does not release the reserved principal. Delivered card inventory is never returned to sale.

Pancake uses the original store and buyer identity to mint an ephemeral customer session. Its dedicated customer transport preserves only that freshly minted Bearer token and permits exactly `POST https://api.waffo.ai/v1/actions/refund-ticket/create-ticket`. Protected merchant GraphQL queries use the original tenant snapshot; counts and bounded lists must agree before empty results permit the first submission. A returned ticket, even one marked succeeded, is not an executed refund. Signed refund notifications only advance the query schedule. The authoritative native refund execution query produces completion/failure proof.

New signed original-payment callbacks freeze a real PAY identifier and explicit `chargedAmount`, including collected tax. Missing actual charge is not replaced by list-price fields. Older orders without that evidence remain available for manual reconciliation; no guessed PAY is emitted. The Linux DO signed callback or authenticated original-payment query freezes the verified native full payment.

Linux DO supports only its documented full refund, `POST https://credit.linux.do/epay/api.php`. Only an authenticated exact success ACK authorizes completion. It documents no refund identifier or authoritative refund query; the recorded `ldc-ack-<semantic-hash>` is explicitly an internal ACK reference. Timeout/error stays unknown/manual and is never automatically re-submitted. Generic merchant Epay remains manual/unavailable; no universal refund endpoint is fabricated. See [official Linux DO API](https://credit.linux.do/docs/api) and the pinned [Pancake customer API](https://github.com/waffo-com/waffo-pancake-sdk-go/blob/v0.11.0/customer.go).

The existing cancellable store worker processes bounded refund batches. Only the original seller or a current root administrator may explicitly trigger `POST /api/store/orders/:id/refunds/:refund_id/reconcile`; its body is empty or `{}`. It accepts no amount, recipient or completion evidence. Ordinary buyers/admins cannot trigger this endpoint. The API reports the existing refund view; `awaiting_provider` never means refunded.

Release qualification still requires the central capability-4 schema/floor gate, real PostgreSQL concurrency and old-writer/old-callback acceptance. Local fake-HTTP tests do not establish production provider acceptance, and no real payment, refund or email is sent by this validation.
