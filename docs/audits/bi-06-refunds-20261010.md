## Confirmed local defect

`merchantStorePancakeRefundExecutionResult` checked a ticket's original PAY and
ORD, but did not check the separate execution's `PaymentID`. Its GraphQL query
also omitted `paymentId`, although the response type already declared it.

A matching ticket plus an execution with another, missing, whitespace-prefixed,
or ticket-shaped payment ID could produce either successful-refund evidence or
verified-failure evidence. Failure evidence matters because it can permit the
caller to release a refund reservation. This finding is about the acceptance
of synthetic decoded evidence. It is **not** evidence of a real provider returning
such a response, an actual wrong-recipient refund, or a database balance change.

The patch requests `paymentId` on the execution and checks that it is nonempty
and exactly matches the frozen original payment before producing either kind
of evidence. It does not copy the order-sync implementation from #704. The
positive shared provider fixture now includes the field actually requested.
Existing assertions are retained; no test is changed to accept the defect.

The [official Orders & Payments documentation](https://docs.waffo.ai/api-reference/endpoints/graphql/orders-and-payments),
read on 2026-10-10, documents `paymentId` on both refund lookup and the refund list
filtered by `refundTicketMerchantExternalId`. It distinguishes actual execution
`pspAmountDetails` from requested ticket amounts. The
[pinned SDK guide](https://github.com/waffo-com/waffo-pancake-sdk-go/blob/v0.11.0/docs/graphql-guide.md)
supplies the existing ticket/payment/order links. No dependency upgrade or new
money-moving API is added. Actual merchant schema access remains unverified.

## Permission and recovery observations: source only

The inspected `storeRefundAccess` permits buyer/seller/root access as applicable,
and limits decisions to the seller or root; ordinary administrator status alone
is not equivalent to root. No live role/HTTP/pickup authorization result was
measured. Payment-ID binding is not a substitute for that authorization check.

The existing dispatch source uses a one-way `SubmitCount` and records an unknown
state before submission. Notifications schedule a query rather than constitute
a returned-money receipt. Provider evidence is saved separately from local
reconciliation. This patch does not change these mechanisms; their behavior
under timeout, lost receipts, concurrent callbacks, insufficient balances, and
local transaction failure remains unverified in PostgreSQL during this run.
